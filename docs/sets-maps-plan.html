Where they stand

A million keys or items, each loop in a function of its own (bench/kernels/nullables.ww, the best of five, pinned; the set and the map of 666,667 ints):

LoopmsWhat a region does with it
for (n in set)4.0Taken for a list (iteri), which misses every time round: dropped, made again (42ba9d1), dropped again; 512 misses, then the VM's.
set.contains(i), i in set26.4No region: the call (R_INVOKE, and a SWAP for in) is the VM's, and too little is left around it.
map[i] ?: 028.5A region, the read (R_GET_INDEX_SS) the VM's: it leaves and comes back each time round.
map[i] = x—Taken for a list (hsetwi, looked at once): misses every time, 512 in all, then the VM's.
m[w] = (m[w] ?: 0) + 1 over words—Both: the words' for taken as ints (iteri), the set taken for a list (setwi); 512 misses.
for ((k, v) in map)3.4No region (IterNextPair is the VM's).

The misses cost twice: each region is made, used until 256 misses, made again, and missed out again. The VM alone already does the plain cases quickly (a for over a set, 6 ns an item); what native code can win is in the lookups (26 to 28 ns each now) and in keeping the loop around them native.

How a map and a set are kept

Both are a ValueMap (value.h): the entries in the order they were added, each a key, a value (unused in a set), whether it is live, and its key's hash folded to 32 bits; and an index of slots, a power of two in size, each 0 (empty), the entry's place plus one, or gone. A key's hash is keyHash times 0x9E3779B97F4A7C15, its top 32 bits; the first slot tried is the hash shifted down to the index's size, then the next, and on. Two keys are the same where keysEqual says so: an int and a byte or a float of the same number are one key, a char and a one-letter string are one, a string by its characters, a value of a value type by its fields, an object of a class with its own == and hashCode by those (D26). A key added or taken out moves the map's version on; a for going through it stops with an error once it has. Values are stored as they are; the collector neither moves objects nor needs to be told of a store (no write barrier).

The parts

  1. Part 0: no list steps on a map or a set. Where the frame shows a map or a set as the region is made, the steps for lists (iteri, iterf, idxw, setwi, the looked-at-once h steps) are not made for it: the instruction stays the VM's. Nothing new; it ends the 512 misses above. Small and safe whatever is decided below.
  2. Part 1: lookups. map[k] (the value, or null, into the slot, then ?: and != null as for lists), map.containsKey(k), set.contains(k) and k in set / k in map (into the flag): one step each, the map's or set's kind and core checked by it.
  3. Part 2: setting a key's value. map[k] = v where the key is there: the value written in its entry. A new key: added by the VM (question 3). set.add(k), map.remove(k) and the like: the VM's, or the same way as a new key.
  4. Part 3: going through. for (k in set), for (k in map.keys) and for ((k, v) in map): the next live entry's key (and value) into their slots, the version checked each time as the VM checks it (a change leaves for the VM, which stops with the error).

Looking a key up: in C++ or in the step

Two ways, which can be had one after the other:

  • A call into C++ from the step, as mkbox calls the VM for a box (since 2026-11-15) and the push steps call it for room (42ba9d1): ValueMap::find with the key as the slot holds it. Every kind of key, exactly the VM's answer (a class's own == is the one case that cannot run there: it runs code, so the step leaves for the VM where the map's keys may have one). What it saves is leaving and coming back (the region's registers written back and loaded, the VM's dispatch): most of the 26 to 28 ns.
  • Probing in the step, for ints and strings: the hash worked out as keyHash does for them (an int's own bits; a string's kept hash, the VM's where it is not worked out yet), the slots tried in turn, a stored key compared as keysEqual would (an int or a byte by its number; a string by being the same object, or its length, width and characters); any other stored key met (a float, a char, an object) the VM's. No call at all, but a second copy of the table's rules, to be kept in step with value.cpp.

The spike and its gate

Part 0, then part 1 by the C++ call, timed on bench/kernels/nullables.ww against the commit before. Gate: set.contains(i) over a million at 10 ms or less (26.4 now), map[i] ?: 0 at 12 ms or less (28.5), no other row slower. Where the call misses the gate and probing in the step would meet it, probing for ints and strings; where neither, stop there.

What does not change

  • The table itself (ValueMap), its hashing and its rules for keys: native code follows them or leaves.
  • A for over a map changed as it goes stops with the same error, from the VM.
  • Maps and sets of another core, or frozen, or a view of a map's keys or entries: the VM's (as for lists).

Risks

  • A class's own == or hashCode runs WinterWolf code, which a step cannot: the step leaves for the VM where the key it looks up, or a stored key it meets, is an object of a class (mayOwnKeys).
  • Equal keys of two kinds (1 and 1.0, 'a' and "a"): a probing step that meets a stored key of another kind leaves rather than decides.
  • A new key's index: growing the index from a step means the C++ call (question 3); keeping a pointer into the entries across a call that may add would leave it behind, so no step keeps one.
  • Code layout: as every change to the VM's loop, timings move by a few percent with the executable's layout; each is checked with native code off as well.

2How a lookup is done

  • The C++ call first, probing in the step for ints and strings only where the gate wants it.
  • Probing in the step from the start, for ints and strings; any other key the VM's.
  • The C++ call only.

Recommended: the C++ call first. It is exact for every kind of key with no second copy of the table's rules, and most of what a lookup costs now is the way out and back, which it takes away.

3A new key

  • Added by a C++ call from the step (ValueMap::set, as makeRoom grows a list), the region going on.
  • Left to the VM: the step leaves (no miss) and the VM adds it.

Recommended: the C++ call. A map filled in a loop (counts[w] = ...) adds a new key often; leaving each time would cost what it costs now.
