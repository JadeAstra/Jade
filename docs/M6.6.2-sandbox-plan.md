# Plan: M6.6.2, a sandbox for tests

Asked for 2026-11-04: a world for tests in which files, the network and processes are
make-believe, so that nothing outside it is touched, and in which the test can make the rare
failures happen on purpose (a directory that fails half way through being listed, a disk that
fills, a connection that drops after 100 bytes). Nothing is built yet; this page is for the user
to read and decide on.

## In short

Every file, stream, process and socket operation of Astra is already a C++ function of the
standard library's (`__file`, `__io`), and so are the clock, the timers, randomness and the
installed fonts. The plan puts one C++ interface, the **host**, in front of all of them:

- the **real host** is today's code, moved behind the interface and otherwise unchanged;
- the **virtual host** keeps everything in memory: a file system, a network, programs to run, a
  clock that moves only when the program waits, a fixed random seed; and a **list of faults**
  that say which operation fails, where, when and how.

A test asks for the virtual host with `Sandbox.run { ... }`. Inside it, the real host cannot be
reached at all: that is what makes "nothing outside is touched" a guarantee rather than a habit.

```astra
@Test fun reportsAHalfReadDirectory() {
  Sandbox.run {
    files.write("/data/a.txt", "1")
    files.write("/data/b.txt", "2")
    files.write("/data/c.txt", "3")
    faults.add(Fault.list("/data", after = 2, error = "the device is not ready"))
    val error = assertFails { Path("/data").list() }
    assertContains("${error.message}", "the device is not ready")
  }
}

@Test fun survivesADroppedConnection() {
  Sandbox.run {
    network.host("example.test", 80) { peer ->
      peer.send("HTTP/1.1 200 OK\r\nContent-Length: 1000\r\n\r\n")
      peer.send("x".repeat(100))
      peer.reset()                      // the far side goes away 100 bytes in
    }
    assertFails { fetch("http://example.test/") }
  }
}

@Test fun timesOutWithoutWaiting() {
  Sandbox.run {
    processes.add("slow") { process -> process.waitForever() }
    assertFails { Process.run("slow", timeout = 5.minutes) }   // takes no real time: the clock is the sandbox's
  }
}
```

Java has Jimfs, Python pyfakefs and Go `fs.FS` and fake listeners for parts of this; putting
the files, the network, processes, time and faults behind one interface, in the runtime itself,
is what lets one test arrange all of them and reach the rare paths.

## What the host covers

From a survey of the C++ (2026-11-04):

| Area | Where now | What the host gives |
|---|---|---|
| Files: whole-file read and write, exists, kind, size, times, delete, mkdir, move, copy, list, canonical, permissions, temp files and directories, absolute | `__file`, 24 functions (stdlib.cpp) | a file system |
| Streams on files, pipes and sockets: open, read, read a line, read all, write, close | `__io`, 8 functions (io.cpp) | streams |
| Processes: start, wait, collect output, alive, kill, pid, this program's pid and command | `__io`, 8 | programs |
| Sockets: connect (with name lookup), listen, accept, ends, read timeout, half-close | `__io`, 6 | a network |
| Time: `clock()`, `Instant.now`, sleep, joins and waits with timeouts, timers | builtins.cpp, threads.cpp | a clock |
| Randomness: `Math.random` and the rest, seeded from the machine | builtins.cpp, vm.cpp | a seed |
| Installed fonts: families, typefaces, find, fallback, and reading font files | `__text`, 7 functions | a font folder |
| Clipboard | `__jade` | an in-memory one (Jade has one already, `clipboardOwn`) |
| The number of cores | `__parallel.cores` | a number |

Left as they are: windows and drawing, which already sit behind an interface of their own
(`jade/platform.h`, with `window_absent.cpp` for no windows); what the compiler reads (the
program's files, the cache), which is the test's own source; standard output and input, which
the test runner reads already.

The I/O in io.cpp is about 470 lines for Windows and 415 for Linux under one shared layer of
540; the host goes between that shared layer and the system code, so the 22 functions of
`__io` are written once on top of it, as now.

## How each part works

**Files.** A tree of directories and files held in memory: contents as bytes, times, the
write bit, symbolic links. Paths are of one style for a sandbox, Linux's (`/data/a.txt`) by
default, or Windows' (`C:\data\a.txt`, names compared without case) when asked for, so that
code that builds paths can be tested both ways on either machine. A size limit makes "the disk
is full" possible. The temporary directory and the program's own directory are in it.

**Streams.** A file stream reads and writes the virtual file; a pipe and a socket are a buffer
between two ends, each end able to close, half-close or reset.

**The network.** Names resolve only to hosts the test declares; anything else is "cannot find
host". `network.host(name, port) { peer -> ... }` gives a far side written in Astra, run as a
task of the sandbox, which reads what the program sends and answers; `listen` in the program
makes a port a test can connect to with `network.connect(port)`. No real socket is opened.

**Programs.** `processes.add(name) { process -> ... }` declares a program: it is given its
arguments, environment and input, and writes output and errors, ends with a code, or never
ends. Starting a program not declared is "cannot start".

**The clock.** Time in a sandbox moves only when everything the program is doing waits: a
sleep, a timer, a timeout, a read with nothing to read. The clock then jumps to the next time
something is due. A test of a five-minute timeout runs at once and the same way every time, and
`clock.advance(2.seconds)` moves it by hand. Randomness starts from a fixed seed unless the test
gives another.

**Faults.** `faults.add(...)` takes rules, each saying:

- which operation: open, read, write, list, delete, move, permissions, connect, accept, send,
  start a program, and the rest;
- where: a path or a pattern of paths, a host and port, a program's name;
- when: always, the nth time, after so many bytes or names, after so much time;
- what: an error of the kind the system gives (not found, no permission, the disk is full, the
  device is not ready, the connection was reset, the time ran out), a read or write that does
  only part, or a delay.

A fault goes through the same error path in the C++ as the real failure, so the program sees
the same exception and message it would. That is the point: the rare paths are the real ones.

**Nothing escapes.** Inside `Sandbox.run`, every operation goes to the virtual host; there is
no way to reach the real one, and an operation the virtual host has no form of throws "not
available in a sandbox". Workers and the cores of a parallel section started inside it share it.

## In tests

- `Sandbox.run { ... }` anywhere, in a test or a script; it ends with the block and leaves
  nothing behind.
- `@Sandboxed` on an `astra test` function, or on a whole file, runs it in a new sandbox, as
  `@TempDir` gives a directory now.
- What the sandbox did can be read afterwards for checks: `files.read(...)`, what a peer
  received, which faults fired.

The suite keeps a small set of tests on the real host, marked as such, for what only the real
systems can show: Windows junctions, a real TCP stack, real programs. The rest of the tests that
touch files and the network today can move to the sandbox, and stop leaving or needing anything
on the machine.

## Cost

- **Speed:** one indirect call more for each file, stream, process or socket operation, nothing
  beside a system call; nothing for code that does no I/O. The benchmarks are measured before
  and after step 1.
- **Work:** about six to eight days in all, in the steps below. The most is in making the
  virtual files and network behave like the real ones closely enough to be trusted, and in the
  clock, which has to know when every thread and task of the program is waiting.

## Steps

Each a commit or a few, with the quick check; the full check and Linux at the end, as for M6.6.

1. **The host interface, and the real host behind it.** No change of behaviour: the suite and
   the benchmarks as before. (1 day)
2. **Virtual files, `Sandbox.run`, and faults on files.** With it the test of `list()` failing
   half way through (bug 6), and a first set of tests moved onto the sandbox. (2 days)
3. **The clock and randomness.** Sleep, timers, timeouts and waits on the sandbox's time.
   (1 to 2 days)
4. **Programs.** (1 day)
5. **The network.** Names, ports, peers written in Astra, faults on connections. (1 to 2 days)
6. **Fonts and the clipboard**, from a folder of fonts kept with the tests. (half a day)
7. **`@Sandboxed`**, the tests that can move, and the README and porting.md. (half a day)

## To decide

1. **The name**: `Sandbox`, or another (`TestHost`, `Simulated`).
2. **Whether `astra test` runs every test in a sandbox by default**, with `@RealHost` to opt out
   (safer, and the rare paths are always at hand), or only those marked `@Sandboxed`.
3. **Whether programs, not only tests, may use it**, for a dry run of something that would
   change files.
4. **The default style of paths**: Linux's on every machine (the same everywhere), or the
   machine's own.
