How: WinterWolf first, native code taught what it lacks

  • Written in WinterWolf, as a program would, in functions of their own, so that native code makes regions and loop templates of them; where native code leaves a loop to the VM, it is taught that loop's shape (a stencil, a template), as was done for the pixel loops, rather than the loop being moved into C++.
  • C++ only where native code cannot come near after that, and then as a public piece any program can call (as Image.writePixels), never a private one.
  • The same results: each encoder's files read back as the same pixels, and as small as now or smaller; each drawing the same pixels as now, unless a question below decides otherwise.
  • Each part timed against the C++ it replaces or a C++ yardstick in bench/kernels/timings.cpp, and its row in timings.html.

The indices in WinterWolf (bench/spike/gif_nearest.ww): the same indices as the C++ on every picture tried (the photo, a crop, noise with see-through pixels, a ramp, palettes of 2 to 256 colours and one with colours twice, each method, and the GIF files: 85, byte for byte); its search through the palette sorted by green, which tries a few colours where the C++ tried all 256, its tables zeros until used. 1.4 times the C++ undithered, 3 times dithered: kept out by the gate (a slower piece does not replace a quicker one), the C++ left in place, now a member every program can call, Grid<Color>.paletteIndices(palette, method), each pixel's index as bytes (what a file of indexed colours holds).

Why native code did not carry them: each loop is made whole, but holds more values at once than its nine registers for whole numbers. A way out after each check must write back every variable changed so far, so they are all alive at once, and what is spilled to memory is spilled everywhere: the hot path's values (the LZW loop's prefix, key and code found: four loads and stores each time round, of 17 steps) as much as the cold path's. The C++ compiler keeps them in registers on the hot path and writes them only on the way to the cold one.

What native code was taught on the way, for every program:

  • Items of two lists meeting in one variable (c = cells[key], else nearestOf[key]): every list read so made again as a list of ints, where the region was refused.
  • One more try at making a region (four, not three), where the first ones each uncover one thing to change.
  • Lists and fields looked at once in a loop that calls out and comes back: every way back in looks at them again, where before a call anywhere in the loop meant none was (the indices' loop 8.4 ms to 4.6 held; tests/native_relook.ww, which fails without the looking again).

Tried and dropped: what to spill chosen by how often each value is used as a guess has it (the loop's head once each time round, a branch halving it, a branch round a call taken 1 time in 16, one straight back round the loop 7 in 8, an inner loop four times, the head's own counters spilled last), not by where it is written. It helped the indices' loops, but where a region's hot part is an inner loop (the blur kernel: the outer loop over a pixel's four parts, four times a row, round the loop along the row) it kept the outer loop's counters and spilled the inner one's values: 13% slower. Without counts of what really runs, a guess that serves one loop costs another.

The first call (2026-11-17, the user: "look at this"): a loop's region is made the second time round its first run (not, as first said here, on its second run), so a GIF written once is native too; but making them is paid on the first call: the 1000 by 1000 photo's first GIF took 66.6 ms to the later ones' 34, of which 21.5 ms making 32 functions' regions (registers 10, analysis 3.2, liveness 2). Liveness and the clashes between values were kept as sets, made afresh for each instruction on each pass and after each spill, and each value to be set aside was picked by walking the rest through map lookups: now rows of bits over the region's values numbered in their own order, the sets made only where asked for, the picks in arrays; the same picks in the same order, so the same code (every region of the tests, the kernels and the GIF parts dumped by both builds: the same, 2,300 and more). 21.5 ms to 14.2; the first GIF 66.6 to 48. WW_TIME_NATIVE now also tells colouring, spilling, liveness again, and the code made. Left: analysis 3.1, the code made 2.2, 11 regions refused after their analysis; making regions while the VM runs on (on another core) would take it off the first call whole.

Next, to reach the gate: a value's life split between a loop's hot path and its cold one, kept in a register on the first and in memory on the second, written back on the way into the cold path (what C++ compilers do); or more registers for native code (it has nine of the processor's sixteen). Either is a piece of native code's own, before part 1 is tried again; the user's to choose, and whether part 2 (PNG) goes first meanwhile.

Questions for the user

Each with the recommendation and why.

1The encoders now in C++ (PNG's, WebP's): written again in WinterWolf?

  • Yes, each behind its gate: written in WinterWolf, native code taught what they need; kept only where they reach their gate, the C++ deleted then.
  • No: left in C++, made faster there.

Recommended: yes, behind the gates. It is what "keep them in ww" asks, and what native code learns on them (hash chains, bit output, tables) serves every program; a gate keeps a slower encoder from replacing a quicker one.

Decided2026-11-17, the user ("Yes, behind gates").

2PNG: faster at the same size, or faster still a little larger?

  • No larger: each file as small as now or smaller; the speed from better code only.
  • A little larger allowed: a quicker search for repeats (as fpng and libdeflate's fast levels do), files up to 5% larger, several times faster.

Recommended: no larger, with the quicker way offered as a level (save(path, quality) already takes one) for a program that wants it.

Decided2026-11-17, the user ("No larger").

3Smooth lines: the same pixels exactly, or within one level?

  • Exactly the same: the coverage worked out as now, only less of it.
  • Within one level: a quicker way to the coverage along the line; a pixel's edge may differ by one level of 255.

Recommended: within one level: no eye tells, and it is where most of the speed is; the tests that compare pixels compare lines with a tolerance already.

Decided2026-11-17, the user ("Within one level").

4blurred: the same pixels, or a level off here and there?

  • The same pixels: what can be had without changing any (a running sum for large radii, the work split across cores).
  • Floats: several times faster, a pixel a level off here and there.

Recommended: the same pixels: a blur is often compared against a saved picture, and the work split across cores gives most of the speed anyway.

Decided2026-11-17, the user ("Same pixels").

5The order

  • As above: GIF, PNG, WebP, pictures and blending, lines, blur, calls.
  • Calls first: what is written in WinterWolf after it has quicker calls from the start.

Recommended: as above: the encoders are written as single loops, which native code takes whole without calls; calls matter most to code made of small functions, and their last spike failed.

Decided2026-11-17: as recommended, the user not asked otherwise; theirs to change.
