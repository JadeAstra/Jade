  • Addresses are only numbers: making one never asks DNS (Java's InetAddress.getByName does, which hides a wait). Names are looked up with Dns.
  • An address arriving as IPv4 mapped into IPv6 (::ffff:1.2.3.4, from a socket listening on both) is given as the IPv4 address.
  • Waiting calls (a lookup, a receive) go through VM::blocking, as TCP's do: a thread waits with the lock let go, a task is set aside.
  • In a sandbox, UDP and DNS are refused with an IOException, as Unix domain sockets are: its network is the simulated one of M6.6.2, which has TCP only.
  • Secure random numbers come from the system: BCryptGenRandom on Windows, getrandom on Linux. randomInt has no bias (it rejects and draws again).
  • Windows reports an ICMP "port unreachable" as a failed later receive on a UDP socket; that is switched off (SIO_UDP_CONNRESET), as Linux does by default.

Questions

Each came with a recommendation; all were taken as recommended on the go-ahead of 2026-11-20.

1The address types' names

  • IpAddress and SocketAddress, numbers only, with Java's InetAddress and InetSocketAddress as errors naming them: clear names, and no hidden DNS wait.
  • Java's names, with Java's behaviour (a name looked up on making one): ported code as written, the hidden wait kept.

Recommended: IpAddress and SocketAddress.

Decided2026-11-20, as recommended.

2Socket.remoteAddress: text or an IpAddress?

It is text today ("127.0.0.1"), and in a sandbox it is the host name the program connected to ("example.test"), which is no address. Recommended: keep it as text; a Datagram's from is a SocketAddress, since UDP has no sandbox form.

Decided2026-11-20, as recommended.

3Listening with no address given

Today a ServerSocket with no address takes IPv4 connections only. Recommended: both IPv4 and IPv6 (one socket, IPV6_V6ONLY off), as Java and Go do; IPv4 alone where the machine has no IPv6. The same for a DatagramSocket.

Decided2026-11-20, as recommended.

4UDP's shape

Java fills a DatagramPacket in place. Recommended: udp.send(data, to) and udp.receive() giving a Datagram(data, from), with no packet object. A receive makes new bytes of the size that came, which a DNS server's few thousand queries a second do not notice.

Decided2026-11-20, as recommended.

5DNS: the system's resolver, or a DNS client of our own?

Recommended: the system's resolver in the standard library (addresses of a name, the name of an address). Records such as MX and TXT need a DNS client that speaks the protocol; JadeMail and JadesDomain have their own, which port as they are.

Decided2026-11-20, as recommended.

6SecureRandom's shape

Recommended: an object with Math's names (random(), randomInt(low, high)) plus bytes(n) and fill(bytes); no instances, since there is nothing to keep.

Decided2026-11-20, as recommended.

7Password hashing

Recommended: Argon2id (RFC 9106), the current first choice for new passwords, and PBKDF2-HMAC-SHA256, which JadeLib's stored hashes use. No scrypt or bcrypt.

Decided2026-11-20, as recommended.

8How much RSA

The layout said "RSA for verifying". JadeMail's DKIM makes RSA key pairs and signs with them. Recommended: RSA key pairs, and PKCS#1 v1.5 and PSS signatures both ways, in constant time; no RSA encryption (OAEP) and no RSA key exchange.

Decided2026-11-20, as recommended.

9TLS features

Recommended: TLS 1.3 first, then 1.2 with ECDHE and AEAD only; SNI, ALPN, session tickets, STARTTLS; client certificates on request. No 0-RTT data (it can be replayed), no renegotiation, no compression. Revocation is not checked, as Go and the browsers' own TLS libraries leave it.

Decided2026-11-20, as recommended.

10HTTP versions

Recommended: HTTP/1.1, client and server, and WebSockets; HTTP/2 left until something needs it (every server and client still speaks 1.1).

Decided2026-11-20, as recommended.
