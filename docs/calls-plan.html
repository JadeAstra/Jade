What it is

Native code cannot make a call. Where a loop calls a function that is not put in place, the region leaves at the call: what it holds in registers is written back to the frame's slots, the VM makes the call, and when the call returns the VM comes back into the region at the instruction after it, which loads the registers again. The plan is for the region to make the call itself and go on, the loop's machine code never left.

Three things follow, in order of what they are worth:

  1. A loop with a call is never slower in native code than in the VM. Today leaving and coming back costs about 5 ns on top of the call, so a loop that does little but call runs slower as native code than without it.
  2. A loop with a call keeps what the region does once for a loop: lists and fields looked at once as the region starts, fields held for the loop and written back at its ways out. Today any VM work in a loop that does not end the function switches all of that off, as a way back in starts afresh.
  3. A loop around a method call gets a region at all. Today such a loop is left to the VM whole: one instruction of five or so being the VM's is too little done between what the VM does (Region::worthIt).

A program behaves the same with it as without it: answers, errors and their messages, stack traces, other threads' turns, tasks that wait. The tests show it by running every test with native code, with the VM alone and in the interpreter, as now.

How a region leaves and comes back today

  • Islands. An instruction a region does not do is an island (Region::transfer): the region's steps before it jump to a way out, whose stores write back every slot the region holds in a register or has not made yet (a copy, a whole number of a list), and whose last step returns to the VM the instruction to go on at and the stack's top. An island on the straight way to a return or a throw ends: the VM never comes back.
  • Ways back in. Every other island's next instruction is a way in (entries, resumed): the region's machine code has a label there whose loads read what the region keeps in registers, and the instruction's word in the run code is patched so that the VM, reaching it, calls VM::nativeEnter.
  • Each time in, nativeEnter finds the region by its head among the function's regions (a search of a short list), makes a fresh RegionContext (the attention flag, the core, the lent object, the lists and fields looked at once, the loop templates' words, the globals, the closure's upvalue cells; some 700 bytes, set to zero), and runs the machine code. A way in other than the first runs no prologue: what was looked at once is gone. That is why lookAtListsOnce and the fields held for a loop are made only where every island ends the function.
  • A miss. A quick way that cannot is counted; past a limit, the region's ways in are the VM's own instructions again.

How the VM makes a call

  • Quick calls. CALL, R_CALL, INVOKE, INVOKE_OWN and R_INVOKE enter a closure at once (QUICK_CALL) where nothing is to be done first: the arguments fit, no enum to settle, room for the frame, no collection due (bytesAllocated_ <= nextGC_) and no other thread waiting (attention_). The caller's frame->ip is set to the instruction after the call, a frame pushed, and the callee's run code goes on in the same loop; its RETURN pops the frame and goes on in the caller. A method is found by name in the object's class (cls->methods), the place's cache remembering nothing yet for calls.
  • Anything else takes the cold way: a safe point (GC_SAFE_POINT, where the collector runs and another thread may take its turn), then callValue: a C++ function, a bound method, a class made, an object's method found by its interface, defaults and named arguments.
  • C++ calling Jade (VM::call, callOn): the arguments pushed at sp_, callValue, and a run of the VM's loop of its own (run(base)) until the frame count is back where it was; NativeCallGuard counts the depth (nativeDepth_, at most kMaxNativeDepth, 200, a stack overflow past it). It is the way a sort's comparison or a list's forEach given by C++ calls a lambda; it has never been timed as a hot way.
  • Exceptions are C++ exceptions (JadeThrow) from where they are thrown to the run whose frames they are in: handled asks tryHandle for the innermost handler (handlers_: a frame, a stack top, an ip), which belongs to that run only if its frame is the run's or above it; otherwise the exception goes on out of the run, to the C++ that called it.
  • Tasks that wait are set aside by throwing FiberSuspend through the C++ stack to runFiber, which a task may do only where nothing of C++ is between (canSetAside: nativeDepth_ == 0). A Jade function called by C++ cannot wait.
  • Threads take turns holding the VM's lock: a thread gives the others a turn only at a call or at the end of a loop's body (G64); native code checks the attention flag at its loops' ends and leaves.

A call made from native code

A step for a call (R_CALL, R_INVOKE; CALL and INVOKE of the stack code) that does what QUICK_CALL asks first and, where all holds, has the call made and goes on; anything else leaves for the VM at the call, as an island does now. Its parts:

  1. Before the call, what the callee could see written back: the frame's slots up to the call's arguments (a captured local is read and written through an open upvalue pointing at its slot; the collector reads the slots), and every field held for the loop (putp). The simplest is everything an island's way out would write (question 2).
  2. The call, by a helper in C++ called from the step: frame->ip set to the call's instruction (for stack traces and for a handler in this frame), sp_ set past the arguments, then the call made and run to its return. Two ways to run it (question 1): through VM::call, the VM's loop run anew for it; or by a way of its own that pushes the frame as QUICK_CALL does and runs the loop until it returns. The callee's own loops have regions of their own as now, entered from its run code.
  3. After it, the result in the call's slot, and what the region keeps in registers loaded again, as a way in loads it; lists and fields looked at once looked at again (question 5).
  4. An exception cannot go through the region's machine code: a stencil has no unwind information, and on Windows an exception thrown through it ends the program. The helper catches it, keeps it (RegionContext), and the step leaves at the call's instruction with the exception kept; nativeEnter throws it there, as the call would have, and the VM's run finds the handler as for any throw. Its stack trace was taken where it was thrown, the region's frame at the call's line. Decided otherwise (question 3): the region's machine code is given unwind information (on Windows a function table for the region's code, RtlAddFunctionTable; on Linux its frame description registered), so that an exception thrown in the callee goes through it to the VM's run as through any C++ frame. The frame's slots are what a handler in the region's own function then sees: with everything written back before a call (question 2) they are right; once only what the callee can see is written back, a call inside a try of the region's own function still writes back everything.
  5. Waiting and other threads' turns. A call of a function that may wait (R1) leaves for the VM, as now; a task cannot be set aside with the region's machine code on the C++ stack. Where the attention flag is up or a collection is due, the step leaves too, and the VM's cold way gives the turn or collects, as it does now (question 4).
  6. Depth. Each call made from native code is a run of the VM on the C++ stack. Past a depth (question 6) the step leaves, and the VM makes the call as it does now, so that deep recursion through loops ends where it does today.

What a loop keeps across a call

  • The context. A call made from native code leaves the region's context where it is: what was looked at once is still there after the call, and the loop templates' words.
  • But a callee may change it. A list looked at once may have been added to (its items moved), a field read once written, a held field read or written by the callee. Either each is looked at again after each call (a few loads a call, nothing to know about the callee), or kept where the checker knows the callee changes no list of that type and no field of that name (its effects: noteCallEffects, changesLists, mayChangeLists), which a call through a lambda or an overridable method rarely allows (question 5).
  • Held fields are written back before every call and read again after it either way: the callee may read them through the object.

Which calls

  • Jade closures: a function called by name, a lambda a function was given, a method of an object's class found by name as QUICK_CALL finds it. These are the calls item 2 leaves.
  • C++ functions (Math, a list's own methods, the text and picture libraries): the VM calls most of them at once already (quickNative), and many are steps of native code (a list's size, an item). Left to the VM at first (question 7).
  • Not: calls with named arguments or a spread, of a class (an object made), of a function that may wait, of a value the region knows nothing of where its call would not be quick in the VM either.

Order, and how each step is checked

  1. A spike: the helper for a function called by name with up to four arguments, on the loops of the table above, both ways of question 1 timed. The gate (question 8): a call made from native code no slower than the VM's quick call, and the loop with a call every time faster than the VM alone. If neither way holds, stop and report.
  2. Calls by name and of lambdas (R_CALL, CALL), with the write-back and the loads, exceptions kept and thrown at the call, the safe point and depth falls back to the VM.
  3. Methods (R_INVOKE, INVOKE, INVOKE_OWN): found by name in the object's class, as the VM's quick way does.
  4. A loop with a call keeps its once-looks: lookAtListsOnce and the held fields allowed where the region's only VM work is calls it makes itself, each looked at again after a call (or kept, as question 5 decides).
  5. worthIt again: a call made from native code counted as the region's work, so that a loop around a method call gets a region.

Each step: a test of its own (answers, errors and their lines, stack traces, a handler in the loop's own function catching a callee's exception, recursion, a callee that waits, threads), every answer the VM's alone and the interpreter's; the suite and GC stress; the kernels and benchmarks against the build before. At the end, ASan (the clang-cl build) and the Linux build, as at a milestone.

What does not change

  • What a program does, its errors and their messages, stack traces, the order things are worked out in.
  • When other threads take their turns, and that a task that waits is set aside.
  • How deep recursion may go before a stack overflow.
  • The run code and the VM's own calls; jade --interpret and JADE_NATIVE=0.

Risks

  • VM::call is slow for this. It was made for C++ calling Jade now and then: a guard, room checked, callValue, the loop's setup and its try. If it costs more than the way out and back in it saves, the call needs a way of its own (question 1), or the gain is the once-looks alone.
  • The C++ stack. Native code calling the VM calling native code: each level a run of the loop on the C++ stack, which a deep recursion through loops could use up before the VM's own frame limit. The depth limit (question 6) is what keeps it as today.
  • A slot the region has not written. A copy made only at a way out (a slot as entered, read where it is) must be made before a call, as at a way out, or a callee reading it through an upvalue sees what was there before.
  • Exceptions kept across the region's return: one kept and never thrown, or thrown twice, would lose an error or report one twice. Each way the step leaves is tested.
  • Threads and the collector must see the frame as the VM would at a call: the slots written back, frame->ip right. GC stress and the thread stress setting run each step.

Questions for the user

Each with the recommendation and why.

1How the call is made

  • Through VM::call, as C++ calls Jade now: nothing new in the VM, but untimed as a hot way, and it may cost more than it saves.
  • A way of its own: the frame pushed as QUICK_CALL pushes it, the loop run until it returns, no guard or callValue on the way. More code in the VM; as fast as the VM's own call can be.
  • Leave and come back, made cheaper: the VM still makes the call, but the region found at once, its context not made anew, its once-looks kept. Smallest; keeps the call's cost and part of the round trip.

Recommended: a way of its own, after the spike times it against VM::call: a call made from native code should cost no more than the VM's quick call, which VM::call is not built for.

Decided2026-11-13, the user: A way of its own, as recommended: the frame pushed as QUICK_CALL pushes it, after the spike times it against VM::call.

2What is written back before a call

  • Everything a way out writes back, and everything loaded again after.
  • Only what the callee can see: captured locals (slots with an open upvalue), held fields, copies not made yet; numbers in registers that nothing else can see kept there across the call.

Recommended: everything at first (the stores and loads exist and are tested), then only what the callee can see once the step works, as its own step: the second saves most where a loop keeps a few numbers in registers, but needs the slots a closure may see known exactly.

Decided2026-11-13, the user: As recommended: everything a way out writes back at first, then only what the callee can see as its own step.

3Exceptions

  • Kept and thrown at the call: the helper catches, the region leaves at the call's instruction with it kept, and nativeEnter throws it there.
  • Unwind information for the stencils, so that an exception may go through the region's machine code: a table for every stencil on Windows and Linux, and every way through checked.

Recommended: kept and thrown at the call. It needs nothing of the system's unwinding, and the VM finds the handler as for any throw.

Decided2026-11-13, the user: Not as recommended: unwind information for the stencils, so that an exception goes through the region's machine code; a table for every stencil on Windows and Linux, every way through checked.

4Calls that may wait, and other threads' turns

  • Left to the VM: a call of a function that may wait leaves the region; where another thread waits or a collection is due, the step leaves and the VM's cold way does it.
  • Done from native code: the turn given and the collection made by the helper, the region going on after; a task that waits set aside with native frames under it (not possible as tasks are set aside now).

Recommended: left to the VM. They are rare in a hot loop, and what they do (a task set aside, a turn given) stays exactly as it is.

Decided2026-11-13, the user: As recommended: left to the VM.

5What stays looked at once across a call

  • Looked at again after each call: every list and field looked at once read again (a few loads); held fields written back before and read again after.
  • Kept where the callee is known to change none of it: by the checker's effects (no list of that type changed, no field of that name written); looked at again otherwise.
  • Nothing kept: once-looks off in a loop with a call, as now.

Recommended: looked at again after each call. It is right whatever the callee does, costs a few loads, and the calls this plan is for (lambdas, overridable methods, large functions) are those the checker knows least about.

Decided2026-11-13, the user: As recommended: looked at again after each call.

6How deep calls from native code may go

  • A limit of its own (say 64 runs of the loop on the C++ stack, below kMaxNativeDepth), past which the VM makes the call as now.
  • kMaxNativeDepth (200), as C++ calling Jade has it: past it, a stack overflow where the VM alone would go deeper.

Recommended: a limit of its own, falling back to the VM: recursion goes as deep as it does today, whatever native code does.

Decided2026-11-13, the user: As recommended: a limit of its own, falling back to the VM.

7Which calls first

  • Jade functions, lambdas and methods, as QUICK_CALL enters them; C++ functions left to the VM.
  • C++ functions too, called by the helper as quickNative calls them.

Recommended: Jade's first. They are what item 2 leaves; the VM's quick way for C++ functions already costs little, and many are steps of native code.

Decided2026-11-13, the user: As recommended: Jade's first; C++ functions left to the VM.

8The spike as a gate

  • A gate: if a call made from native code costs more than the VM's quick call, or the loop with a call every time round is not faster than the VM alone, stop and report before step 2.
  • No gate: build it all and time it at the end.

Recommended: a gate, as for native code itself. The whole gain rests on the call costing no more than the VM's, which is not known yet.

Decided2026-11-13, the user: As recommended: a gate.
