What Jade and Topaz gain first

As much as possible in Jade, C++ only where it is required (the user, 2026-11-08). C++ is required for what Jade cannot do at all (a system call). Where C++ would be chosen for speed (work done for every byte or every pixel), Jade's own speed on such code is looked into first and improved where it can be (the user, 2026-11-08; part zero below), and the choice is made from the numbers. Everything else is written in Jade, on the native pieces Jade already has (string search, Regex, Font.offsets, the rasteriser), and timed: a C++ piece is added only where a timing misses its target, and then with a public Jade API, as every C++ piece has (the user, 2026-10-17). The packages stand on:

  • Files read and written at an offset: a RandomAccessFile (readAt, writeAt, size, sync, close), a thin C++ piece over the system's calls, and Bytes.indexOf from a position (C++, a primitive). On them, in Jade: ByteSource, InMemoryByteSource, PagedFile (cached pages), writeByteDiff, and LineIndex, built in a worker: a second VM that runs beside the window's (Jade's threads take turns, workers do not), finding line ends with the native byte search and sending its checkpoints back as messages.
  • An XML reader in Jade (tier N5's other half), tag by tag rather than character by character, jumping from one < to the next with the native string search and reading a tag's attributes with one Regex: elements, attributes, text, CDATA, comments and processing instructions passed over, the predefined and numeric entities, internal entities under a cap and never an external one, strict well-formedness with line and column in its error. For SVG and the .ovr overrides; public as Xml.parse and its element and text types. Timed on a 1 MB SVG.
  • Base64 in Jade, accepting MIME's line breaks, for data: addresses; timed on a 5 MB picture.
  • Pictures in more formats, read and written: every format that is read is written, and the other way round (the user, 2026-11-08). Read by Image.load whatever the format: PNG (there now), JPEG (baseline and progressive, its EXIF turn applied), GIF, BMP, and WebP (lossy, lossless and with alpha), the user's addition. Written in each: PNG; JPEG baseline at a quality; GIF with its colours reduced to 256 (an octree, dithering optional); BMP; WebP lossy at a quality or lossless, with alpha. GIF and WebP animated, read and written (the user, 2026-11-08): an Animation of frames, each with its delay, how it is laid over the frame before (GIF's disposal, WebP's blending) worked out on reading into whole frames, and a count of loops; an animation written is made into each format's frames and its smallest changed areas. JadeUI wrote PNG only and read an animation's first frame. Decoding and encoding are work for every pixel (Huffman codes, the DCT and its inverse, VP8's prediction, reducing colours): the codecs are C++, as PNG's is, built in Jade and timed, the user deciding at the end whether they move to C++ (question 14); reading and writing a file's header and EXIF is Jade. JadeUI read WebP nowhere: Snips accepts the files and fails on them.
  • The vector tier N3, split by the rule. In Jade, the geometry: a path of lines, quadratic and cubic curves, SVG's path data read into one, curves flattened to the transform's scale, the stroker (butt, round and square caps; miter, round and bevel joins; a miter limit; dashes), affine transforms with save and restore, text through a transform. What is done for every pixel goes through Topaz's own rasteriser, in C++ already for shapes and text; what is new of it is built in Jade where it can be and timed, the user deciding at the end (question 14), which both canvases already share for shapes and text: filling a flattened path non-zero or even-odd (a stroke filled as one shape, so a highlighter does not darken where it crosses itself), linear and radial gradients (focal point, pad, reflect, repeat) as the paint of fills, strokes and text, clipping to a path, the Clear composite, pictures drawn through a transform (nearest, bilinear, bicubic), Gaussian blur. The recording canvas records paths. Written by us, not taken from NanoVG (question 3).
  • Picture operations, each work for every pixel, in C++ built in Jade and timed, the user deciding at the end whether they move to C++ (question 14): scaled (area-averaged when shrinking), transformed, brightness, contrast and saturation, grey, inverted, a colour lookup, flood fill to a mask and filling a mask, counting differing pixels. The editor's tools, layers, selections and undo around them are Jade.
  • Text in Jade: breaking lines for the box engine on the native Font.offsets (a paragraph measured in one call); a cache of fonts at fractional sizes. A native line breaker only if the document timings ask for one.
  • Code highlighting in Jade, driven by a language read from its .lang data, with a templates key so that "${f("x")}" is code inside a string (Jade, Kotlin, JavaScript); a key typed colours only the lines it changed (and what a string or comment opened there runs on to), not the whole file as JadeUI does.
  • In Topaz: Component.invalidate of a rectangle; the system's dark mode asked through Jade's foreign functions (RegGetValueW, as JadeMem calls Windows), not by running reg query; text areas and fields drawing inline objects (InlineObjects).

Whole-list and grid operations

numpy's kind of work, on the containers Jade already has rather than on new array types (the user asked, 2026-11-08; written up for the user's decision, question 15). A List<int>, List<float>, a list of a narrow width (List<int16>, List<float32>, D148), Bytes and a Grid of any of them are each one packed block of numbers already, which is what a numpy array is: an operation on the whole of one is a loop in C++ over the block, at C++'s speed (SIMD where it helps), with one check per call that the list is packed. Part zero's timings are why: after the VM's improvements a Jade loop over pixels is still 8 to 200 times slower than C++, and a JIT is a project larger than a milestone. Nothing new to learn or convert between: a list read from a file, a grid of heights and a picture's pixels take the operations as they are, and what they give goes everywhere a list or a grid goes.

The rules, the same for every operation:

  • Answers as Jade's operators give them. An int with an int stays an int, its overflow an ArithmeticException as + gives (the user, 2026-11-08: checked, not wrapped as numpy's are, so that a.plusEach(b) gives what a[i] + b[i] does). The C++ loop gathers an overflow over a block and looks once: about 10 to 20 per cent slower than numpy's for adding and clamping 64-bit ints, up to twice as slow for multiplying them, nothing for floats, which are not checked, and nothing in practice for bytes and colours, which cannot overflow an int. Where wrapping is wanted (hashes, checksums, the steps of a random number), the …Wrapped forms say so, as &+ and toByteWrapped() do, and are the fastest; with a float, a float; ints divided are whole numbers, a division by zero an error. A narrow list's items are worked on as ints or floats, as arithmetic on them is; a result written into a narrow list is checked against its range as storing it is.
  • Fast where the list is packed with no nulls; any other List<Number> gives the same answers through a loop in Jade, slower. A null among the items is the error arithmetic on a null is.
  • Sizes match, or an IllegalArgumentException saying both; a list may be given a single number in place of a list, for that number with every item.
  • A new list or grid is the result, or, with into = an open list (a writable grid) of the right size, the result written there and nothing made: numpy's out=, for the inner loop of a program that should not make a list each time. A read-only list or grid (a picture's pixels) can be read from, never written into.
  • Not operators. list + x is a new list with x added (the user, 2026-11-07), so element by element is named: a.plusEach(b), not a + b. New array types could have the operators; a later N-dimensional array type, if real numeric work asks for one, can stand on the same C++ loops.
  • One core to begin with; a grid's rows can already be shared out with parallelRows.

An n-dimensional array

For what lists and grids do not cover (the user, 2026-11-08; question 16): data of three dimensions or more (a volume, a picture's colour channels as an axis of their own, the frames of an animation, a batch), parts of an array worked on in place without a copy, an array of one shape combined with one of another, totals along one axis, matrices multiplied. One type, Tensor<T>, on the same C++ loops as the whole-list operations, with T one of int, float, a narrow width (int8 to int32, float32, D148), byte or bool, kept as one packed block with a shape.

Where it differs from lists and grids:

  • Operators. An Tensor is not a collection that + adds an item to, so +, -, *, / and % work item by item, between arrays and with a number: (a - mean) / spread. An int's overflow checked, as everywhere (the user, 2026-11-08), the …Wrapped forms wrapping.
  • Broadcasting, as numpy's: shapes are matched from the last axis, an axis of 1 standing for any length, so that a row of 3 is added to every row of a 100 by 3 array. Shapes that cannot be matched an IllegalArgumentException naming both.
  • Views. Indexing with ranges gives a view of the same numbers, not a copy (numpy's way, where a grid's [xs, ys] copies): changing it changes the array. copy() gives one of its own. A view of a read-only array is read-only (D32).
  • Axes. Totals, means, the least and the most taken over the whole array or along one axis: a.sum(axis = 0).

General picture operations

For the picture work that whole-array arithmetic does not speed up (the user asked, 2026-11-08; question 17): work where each pixel depends on the one before (decoders, dithering, flood fill), reads from a position worked out for it (transforms), looks at its window in a way that is not a weighted sum (median, erode), writes into a few places shared by many (histograms), or would take many passes as arithmetic (saturation, blend modes). Rather than one C++ function for each operation, a few general ones, each choosing its variant by a parameter once per call, not once per pixel, so that each is as fast as a function made for one operation would be, and covers operations no one has listed. The Image methods decided in question 5 (scaled, transformed, adjusted, blurred, floodRegion and the rest) are built on these, in Jade. Each in C++, its answers tested beside a loop in Jade doing the same, timed, and in the table the user decides from at the end (question 14).

Order

Each step is committed with its tests, carried over where they exist and written where they do not; JadeUI's bugs found in the readings (below) are fixed as each part is ported, each with a test. Only the Clang Windows build is checked step by step; the full check comes at the end. Timings are taken as each part is built, against the targets under Speed.

First: Path becomes FilePath (the user, 2026-11-08), so that the vector path can be Path: the standard library, Topaz, the examples, the tests, the C++'s messages and hints, the docs and the language reference, and JadeMem, each in one commit, the suite with its stress settings and JadeMem's tests run on it. D107's name changes; the C++ text engine's own text::Path, a vector path already, stays and becomes the Jade Path's inside.

Part zero: Jade's speed on byte and pixel work

  1. Measured, then improved. The kernels that would otherwise be C++ written both ways, in Jade and in C++, and timed side by side on this machine: a scan for line ends over 100 MB; JPEG's Huffman decoding and inverse DCT over a 12-megapixel photo; a linear and a radial gradient filled over a 4K canvas; a Gaussian blur; area-averaged scaling; a flood fill. The VM profiled on the Jade versions to find what costs (reading and writing single bytes and pixels, bounds checks, small-integer arithmetic, loop overhead, calls in an inner loop), and improved where the change is general, as M6.7 improved it: an instruction for a typed byte or pixel read and write, checks moved out of loops the compiler can prove, whatever the profile shows. Each improvement benchmarked as M6.7's were and kept only where it helps. Then each piece that would otherwise be C++ for speed is built in Jade, and timed, as it is built and again at the end, beside the same work in C++: at the end the user is shown the timings, and decides for each piece whether it stays in Jade or moves to C++ (the user, 2026-11-08; question 14). Written up beside this plan as a table of the pieces, their timings and what the user decided: M10-speed.html, the kernels in bench/kernels. Done 2026-11-08 (2a6d4d2, 5c6f235): the kernels 1.4 to 5.6 times as fast in Jade; the pieces are timed as they are built.

Speed

Jade is interpreted, so each part is timed as it is built, and where Jade is too slow a C++ piece with a public API is added, as M7 and M8 did. The targets, from JadeUI's own uses:

  • Documents: Decided (the user, 2026-11-08): as recommended. a key typed in Snips' DESIGN.html (433,000 characters, about 70,000 words) answered within a frame. JadeUI does everything per key over the whole document; here layout changes only what changed (step 31). Opening it within a second. This is where a native piece (a line breaker, measuring words) is likeliest to be needed.
  • The spreadsheet: a 10,000 by 20 sheet filled, scrolled, moved through and typed in, each within a frame; painting only what is in view, column widths not measured again on every paint.
  • Code: typing in a 5,000-line file within a frame, only the changed lines coloured again; opening it within a quarter of a second.
  • Large text and hex: a file of several gigabytes opened at once and indexed in the background, near the disk's speed, the window answering meanwhile.
  • The map: tens of thousands of features panned and zoomed within a frame.
  • SVG: Decided (the user, 2026-11-08): as recommended. a 1 MB picture parsed once and drawn within a frame; the Lucide icons at once.
  • Pictures: a 12-megapixel photo opened, zoomed, adjusted and flood-filled, each well within a second; undo not keeping 2 GB.

JadeUI's bugs to fix on the way

The readings found about 80, each to be fixed where its part is ported, with a test, and listed in 6.6 as a difference. The largest: in doc, typing at the start of a paragraph after a heading turns it into a heading, formatting is not undoable, a highlight is saved as coloured text, Markdown lists get two bullets; in css, rules after an @import lost, :hover adding no specificity, var() from :root only; in html, a < in text read as a tag, a DOCTYPE wrapping the document; in svg, render throwing on bad path data, S and T curves wrong, opacity replaced rather than multiplied; in sheet, scrolled columns painted over the frozen ones, Delete on a sparse selection clearing one cell, TSV not quoting tabs; in image, an ellipse hit-tested by its box, a see-through fill differing from its preview, merging a hidden layer; in math, x_(n+1) read as a call, results left on the wrong lines after a delete; in hex, a new source keeping the old edits (a save would write them into the new file).
