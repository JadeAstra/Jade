# Plan: M6.7, a faster VM, and two changes to the language first

Started 2026-11-04, when the user said "start M6.7" after M6.6.2's checkpoint. What M6.7 is, is
in gui-plan.md (M6.7) and M6.7-gaps.html; this file is the order it is built in, and what was
decided along the way.

## Order

The VM's rewrite is to come once the language has stopped moving, so the two changes to the
language decided for M6.7 come first.

1. **Task scopes**: `taskScope { task { ... }; task { ... } }` (Kotlin's structured
   concurrency). The decisions are below.
2. **`use { }` checked against each class's own `close()`** (M6.6 choice 8.5i), so that
   `AutoCloseable.close` may say `throws IOException`.
3. **What the VM does now, measured**: the benchmarks of M6.5 part 4, on the Clang and MSVC
   builds, best of five, the machine quiet (memory: the loop is sensitive to where it is placed).
4. **Instructions that name a frame's slots** (registers, as Lua 5) in place of a stack, and
   combined instructions for common pairs (a compare and a jump, a field read and a call). Clang:
   each instruction goes on to the next itself through a computed `goto`, the code threaded as it
   is loaded (D160); MSVC: the cases of a switch. Bytecode files are made again.
5. **Slots that keep only a payload** where the compiler knows the type, and arithmetic chosen by
   type, with no test of the operands' kinds (D178, G17; G20 and G58 if they show in timings).
6. **Values of up to 32 bytes in consecutive slots** (D149): G8, G9, G13, G14, G19.
7. **A generic value type's type arguments kept when the program runs** (G4).
8. **G66** if it shows in timings; then measured against step 3, the docs, and version 0.6.7.

Each step its commit or commits, with the quick check; the full check and Linux at the end of
each.

## Task scopes (step 1)

Decided by the user, 2026-11-04: a scope throws the first failure where it ends, where a `try`
around it takes it; and what it may throw is **worked out by the checker**: what its block throws,
and what the blocks of its `task { }` and `thread { }` throw, counted where the scope ends rather
than where they are started, so that a `try` around a `task { }` inside the scope does not seem
to catch it. A scope given to another function takes only lambdas that throw nothing checked.

As built:

- `task { }` and `thread { }` in the block are the scope's (members of `TaskScope`, the block's
  receiver); `add(job)` makes any other job one of its own, a pool's `submit { }`; plain
  `task { }` outside a scope is as before.
- The scope ends when its block and every job have ended. Where a job fails or the block throws,
  it cancels the other jobs, waits for them to end, and throws the first failure as it was thrown,
  later ones set aside in it (`suppressed`). A job stopping because it was cancelled is no failure.
  A scope that is cancelling starts nothing more. `cancel()` cancels it by hand: it then throws a
  `CancellationException`.
- The block itself is not stopped: it goes on until it ends (its `get()` of a failed job throws).
- Cancelling a task's job with `interrupt = true` (as the scope does) now stops the task where it
  next waits, with a `CancellationException`; a wait it was cancelled at leaves nothing behind (a
  delay's timer, a lock's hold on the event loop). A thread's job interrupts the thread, as
  before.
- **`get()` on the main thread outside a task runs the event loop** until the job is done, and so
  does the scope's wait there: tasks waiting on timers go on, where before the wait could never
  end.
- What the checker needed besides: a lambda run on an object called as `obj.block()` now passes
  on what it throws, as `block(obj)` did (it did not, for `Sandbox.run` too); and in a lambda run
  on a value of a built-in type (a string, an int) or a nullable one, a name the value cannot have
  as a member is looked for further out, as anywhere, where before the call was not checked at all.

## `use` and `close()` (step 2)

`AutoCloseable.close()` says `throws IOException`. The standard library's `use` counts its own
call of `close()` as throwing nothing; at each `x.use { }` the checker adds what the `close()` of
`x`'s type throws: a stream's and a pool's nothing, a class's own what it says, and through a
type parameter or the interface itself the interface's `IOException`.

## The baseline (step 3)

The Clang build of step 2 (baa2969), kept as it is, against which each step of the VM's work is
timed, best of five in turns on the fast cores. In milliseconds: bounce_classes 940, calls 171,
colors_values 2,638, fields 125, jade_layout 1,075, numeric 235, particles 6,910,
points_values 316, simulation 188, strings 1,196.

## Going from one instruction to the next (step 4, first part)

Built with Clang or GCC, each instruction now ends by going straight to the next one's code,
through a table of 256 addresses filled when the loop first runs (D160's computed `goto`); an
instruction with no label of its own (none now) goes through the switch, and MSVC goes round the
switch as before. Against the baseline: calls -8.9%, fields -7.2%, numeric -10.0%, particles
-6.3%, colors -5.3%, bounce -4% to -6%, the rest -1% to -3%. With the jump at the loop's head
alone, numeric was -16% but bounce_values and bounce_moved +3%: the compiler copied it into
some instructions and not others. The code is not threaded yet (opcodes replaced by addresses as
it is loaded), which D160 measured at a further 5%: it waits for the new instructions, which
change the code's layout anyway.
