# Plan: M6.7, a faster VM, and two changes to the language first

Started 2026-11-04, when the user said "start M6.7" after M6.6.2's checkpoint. What M6.7 is, is
in gui-plan.md (M6.7) and M6.7-gaps.html; this file is the order it is built in, and what was
decided along the way.

## Order

The VM's rewrite is to come once the language has stopped moving, so the two changes to the
language decided for M6.7 come first.

1. **Task scopes**: `taskScope { task { ... }; task { ... } }` (Kotlin's structured
   concurrency). The decisions are below.
2. **`use { }` checked against each class's own `close()`** (M6.6 choice 8.5i), so that
   `AutoCloseable.close` may say `throws IOException`.
3. **What the VM does now, measured**: the benchmarks of M6.5 part 4, on the Clang and MSVC
   builds, best of five, the machine quiet (memory: the loop is sensitive to where it is placed).
4. **Instructions that name a frame's slots** (registers, as Lua 5) in place of a stack, and
   combined instructions for common pairs (a compare and a jump, a field read and a call). Clang:
   each instruction goes on to the next itself through a computed `goto`, the code threaded as it
   is loaded (D160); MSVC: the cases of a switch. Bytecode files are made again.
5. **Slots that keep only a payload** where the compiler knows the type, and arithmetic chosen by
   type, with no test of the operands' kinds (D178, G17; G20 and G58 if they show in timings).
6. **Values of up to 32 bytes in consecutive slots** (D149): G8, G9, G13, G14, G19.
7. **A generic value type's type arguments kept when the program runs** (G4).
8. **G66** if it shows in timings; then measured against step 3, the docs, and version 0.6.7.

Each step its commit or commits, with the quick check; the full check and Linux at the end of
each.

## Task scopes (step 1)

Decided by the user, 2026-11-04: a scope throws the first failure where it ends, where a `try`
around it takes it; and what it may throw is **worked out by the checker**: what its block throws,
and what the blocks of its `task { }` and `thread { }` throw, counted where the scope ends rather
than where they are started, so that a `try` around a `task { }` inside the scope does not seem
to catch it. A scope given to another function takes only lambdas that throw nothing checked.

As built:

- `task { }` and `thread { }` in the block are the scope's (members of `TaskScope`, the block's
  receiver); `add(job)` makes any other job one of its own, a pool's `submit { }`; plain
  `task { }` outside a scope is as before.
- The scope ends when its block and every job have ended. Where a job fails or the block throws,
  it cancels the other jobs, waits for them to end, and throws the first failure as it was thrown,
  later ones set aside in it (`suppressed`). A job stopping because it was cancelled is no failure.
  A scope that is cancelling starts nothing more. `cancel()` cancels it by hand: it then throws a
  `CancellationException`.
- The block itself is not stopped: it goes on until it ends (its `get()` of a failed job throws).
- Cancelling a task's job with `interrupt = true` (as the scope does) now stops the task where it
  next waits, with a `CancellationException`; a wait it was cancelled at leaves nothing behind (a
  delay's timer, a lock's hold on the event loop). A thread's job interrupts the thread, as
  before.
- **`get()` on the main thread outside a task runs the event loop** until the job is done, and so
  does the scope's wait there: tasks waiting on timers go on, where before the wait could never
  end.
- What the checker needed besides: a lambda run on an object called as `obj.block()` now passes
  on what it throws, as `block(obj)` did (it did not, for `Sandbox.run` too); and in a lambda run
  on a value of a built-in type (a string, an int) or a nullable one, a name the value cannot have
  as a member is looked for further out, as anywhere, where before the call was not checked at all.

## `use` and `close()` (step 2)

`AutoCloseable.close()` says `throws IOException`. The standard library's `use` counts its own
call of `close()` as throwing nothing; at each `x.use { }` the checker adds what the `close()` of
`x`'s type throws: a stream's and a pool's nothing, a class's own what it says, and through a
type parameter or the interface itself the interface's `IOException`.

## The baseline (step 3)

The Clang build of step 2 (baa2969), kept as it is, against which each step of the VM's work is
timed, best of five in turns on the fast cores. In milliseconds: bounce_classes 940, calls 171,
colors_values 2,638, fields 125, jade_layout 1,075, numeric 235, particles 6,910,
points_values 316, simulation 188, strings 1,196.

## Going from one instruction to the next (step 4, first part)

Built with Clang or GCC, each instruction now ends by going straight to the next one's code,
through a table of 256 addresses filled when the loop first runs (D160's computed `goto`); an
instruction with no label of its own (none now) goes through the switch, and MSVC goes round the
switch as before. Against the baseline: calls -8.9%, fields -7.2%, numeric -10.0%, particles
-6.3%, colors -5.3%, bounce -4% to -6%, the rest -1% to -3%. With the jump at the loop's head
alone, numeric was -16% but bounce_values and bounce_moved +3%: the compiler copied it into
some instructions and not others. The code is not threaded yet (opcodes replaced by addresses as
it is loaded), which D160 measured at a further 5%: it waits for the new instructions, which
change the code's layout anyway.

## The register machine (step 4, the rest): design

Decided by the user, 2026-11-05: the full register machine, Lua 5's way, rather than moving the
hot instructions to slots one family at a time.

**Where register code comes from.** The compiler goes on writing stack code, which the verifier
follows already, knowing the stack's depth before every instruction. As a function is loaded, a
translator turns that code into register code: every slot an instruction reads or writes named
in the instruction, the stack's depth at each point telling which slot a pushed value is in.
The compiler's 8,500 lines, the verifier and the bytecode files stay as they are; the stack code
becomes what the compiler hands the translator. The VM runs only register code.

**What the translator saves.** A local or a constant that the stack code pushes only to be used
at once is not moved: the instruction using it names the local's slot, or the constant
(`GetLocal a; GetLocal b; Add; SetLocal c; Pop` is one instruction, `Add c, a, b`). A result
that the stack code stores into a local is written there by the instruction that makes it. A
comparison followed by a conditional jump is one instruction. Where a value pushed from a local
might be read after the local has changed, the translator copies it first, as the stack did.

**The frame.** A frame's slots are its registers: its parameters, its locals, then the slots its
stack code used as a stack, as many as the verifier's `maxStack`. A call's callee and arguments
are in consecutive slots at the top, as now, and the called frame starts at the callee's slot,
as now. `sp_` is the top of the running frame's slots, set as a frame starts and as one returns
(Lua's `top`): what the collector scans to, and where the C++ pushes when it calls back into
the program. After marking, the collector clears the slots above each stack's top that hold
anything, so that a slot coming back into reach never holds an object already collected.

**Instructions rarely run.** Of the 185 instructions, the ones the benchmarks run are given
register forms of their own. The others are kept as they are, run on the stack: the translator
puts what they take into the slots at the top, as the stack code had it, and gives each the
depth it runs at, from which the VM sets `sp_` before the instruction's old code runs. Their
code needs no change.

**What else changes.** A catch block's handler keeps the slot the error is put in, from the depth
at its TryBegin. A task set aside in a call keeps the slot its result goes to, as now. The
threaded code of D160 and the typed slots of D178 come after, on the register code.

**In parts, each working and measured.** R1: the translator, one register instruction for each
stack instruction, nothing saved yet, the VM run on it; no faster, but the machine is a register
machine and every test passes. R2: locals and constants read where they are, results written
where they go, comparisons joined with jumps; this is where the time is won. R3: the code
threaded (D160). Then typed slots (step 5).

## The register machine as built so far

**Part A** (56696d4): each function keeps the code the VM runs beside its stack code, made as the
verifier passes it, with a line table and its rights' ranges in that code's offsets.

**Part B**: the translator (registers.cpp). It follows the stack code with the verifier's depths,
noting a pushed local or constant instead of moving it; an R instruction names where its operands
are, with the stack instruction it stands for after it, whole, which runs where its quick way does
not do, its operands put where the stack would have had them. Every value noted is put in its slot
before any other instruction, a jump or a place jumped to, and before an R instruction writes a
slot above it, so that every slot below the VM's top holds what was written there while it was
below the top, and the collector needs no change. A slot a nested function captures is never read
through a note. Anything the translator does not expect keeps its stack code
(ASTRA_TRANSLATE_STRICT makes that an error, for testing it). All 360 tests pass on register code,
with every stress setting.

It is not yet faster, and is made only with ASTRA_REGISTER_CODE set. In the same build, numeric
ran in 256 ms on it against 185 on its stack code, fields 160 against 110: the stack code's joined
instructions (MulLocals, AddLocal, StoreLocal) had already taken as many instructions out as the
R instructions do, and each R instruction costs more, decoding three 16-bit operands and testing
for each whether it names a slot or a constant, a branch hard to predict.

**Next**: one-byte operands (a function needing more than 255 slots or constants keeps its stack
code); an instruction for each kind of operand, slot or constant, so nothing is tested when it
runs; a result written straight into the local it goes to, and a comparison joined with the jump
after it. The stack code after an R instruction may be several instructions (`Add; StoreLocal x`,
`Lt; JumpIfFalse t`), run in turn where the quick way does not do, so that an operator the program
wrote, which pushes a frame of its own, still ends where it should.

**Part C** (2026-11-05): R instructions of a byte per operand, one for each kind of operand (slot
and slot, slot and constant, constant and slot), so nothing is tested for it; a result written
straight into the local the stack code stores it in; a comparison joined with the JumpIfFalse
after it. Their slow way is out of line: the R instruction puts its operands where the stack would
have had them and goes to the stack code it was made from, put after the function's own code,
which comes back; so its quick way passes over a fixed length, nothing read to find where the next
instruction is. RGetProp's quick way reads fields of values too (in a box, kept in the value, or
through a reference to a list's item), as GetProp's does. A function needing more than 255 slots
keeps its stack code. There is room for 35 such instructions: the stack code has 220.

Against the stack code in the same Clang build, best of five pinned: numeric -7%, calls -3%,
bounce, particles and points the same, colors +2%, layouts +3% to +6%, simulation +5%, strings
+7%, fields +35%. Small tests show why: where R instructions follow one another the register code
wins (`s += b.mass` -24%, `s += b.position.x` -10%), and where an R instruction's result goes on
to stack instructions it loses (`b.position.x = 1.0` +12%: RGetProp, then Const and SetProp as
the stack code has them). Still made only with ASTRA_REGISTER_CODE set.

**Next**: R forms of the rest of what runs often (SetProp and SetOwn, GetGlobal, constants and
Pop, the arguments of a call), so that stack instructions are rare in the code that runs most.
That needs instruction numbers: the stack code's joined instructions (AddLocal, MulLocals,
StoreLocal and the rest, some 30) never appear in run code, which has R instructions for them, so
the run code can have numbers of its own, the translator turning even the stack code it keeps
as it is (a function of more than 255 slots) into instructions without them.

**Part D** (2026-11-05), in six commits:
- D1: the joined instructions are never in run code, and their numbers are the run code's own.
  The translator has three ways: in full (ASTRA_REGISTER_CODE), joined only (the default, its
  joined instructions made R instructions: faster than the baseline everywhere, numeric -19%),
  and plain (a function of more than 255 slots; ASTRA_REGISTER_CODE=plain to test it).
- D2: R instructions for fields written (absorbing a statement's Pop), globals, upvalues, list
  items, - and !, JumpIfFalse. R instructions read their operands a field at a time where they
  are: a value just written in two stores is handed on by the processor to reads no wider than
  each, and a read wider than them waits for the stores to be done.
- D3: where an R instruction's result goes where the stack would have it, its slow way is the
  stack instruction's own, at once, not out of line and back. A field read followed by another
  stays stack code, so GetProp reads a value inside an object through without copying it.
- D4: shifts by a constant, & and |; quick ways that both kinds of code lacked: a string's or a
  list's size, a getter that only reads its stored field (as a property with a setter alone has),
  the fields of a value being made, in its box.
- D5: fields read through a Ref of any depth (a method of a value held in a list's item);
  RGetProp writes its result in one store of 16 bytes (Value::setWhole), since what reads the
  whole value next (a call's arguments) waited for the two or three stores it made.

Two lessons from it. The slow ways that cost most were ones both kinds of code took; register
code paid for each a jump out and back as well, so making them quick helped both. And the cost of
an R instruction is mostly in how its result is stored and next read, not in the work it does.
Writing every int and float result whole, as RGetProp's, was tried and cost more than it saved.

After D5, against the default in the same build: particles -14%, calls -10%, fields -9%,
colors_classes -8%, bounce_values -6%, numeric -5%, the layouts -1% to -4%; points and strings
within 1%; simulation +2% to +6% (building its grid: a map and lists, mostly native work). The same
code built twice moves a benchmark by up to 5%, so differences under that are not told apart.

**D6**: the register code in full is the default (the user's choice, 2026-11-05, with simulation's
gap left for later). ASTRA_REGISTER_CODE=joined makes the code part D started from, and =plain
the stack code, for testing and timing those ways; the suite passes in all three.

## Threaded code (step 4, last part)

Each instruction of run code is now 8 bytes, then its opcode and its operands as before: built
with Clang or GCC, the 8 bytes hold the address of the instruction's code in the loop, written
the first time the loop runs the function (D160), so that each instruction goes on to the next
with one load where it took two (its opcode, then the table). The translator is unchanged; a last
pass (threadCode) puts the bytes in and moves every offset in the code, its line table and its
rights. While an instruction runs, `ip` is past its opcode as before, so no operand is read
differently; what reads the instruction after (readThrough) skips the 8 bytes. Code no path
reaches is left out of run code now: copied as it was, its joined instructions read as the R
instructions of the same numbers. Built with MSVC the bytes are not used.

Three measurements on the way. A table of addresses beside the code, one for each byte, was 12%
to 14% slower (one more value to keep in a register). With the address in the code, clang merged
the ends of most instructions into one shared jump, which the processor then predicts as one:
numeric 10% slower than before; each end is now made different with an empty asm statement
(ASTRA_APART), which keeps them apart. Each instruction started at a multiple of 8 bytes, so that
its address never spans two cache lines, was 1% to 4% slower than without.

Against the code before, in the same build: numeric -11%, points_classes -6%, fields -5%,
colors_values -5%, bounce_values -3%; the rest within 2.5% either way. Run code is close to three
times as large, as D160 expected (numeric's mandelbrot: 474 bytes, now 1,318).

## Two-byte opcodes, and the instructions as functions (step 4, after threading)

**Two-byte opcodes** (b37f396): run code's opcodes are two bytes, so its own instructions have
numbers of their own (275 in all) instead of borrowing the joined instructions'. Threaded, the
opcode is not what takes an instruction to its code, and the byte costs only size. numeric
showed +6.5%, which turned out to be where clang happened to place the loop's code: with its
jump targets aligned to 16, 32 or 64 bytes numeric ran from 144 to 162 ms in either build, and
profile-guided builds of both ran it the same.

**Why the loop was a lottery.** run() was one function of 32,000 machine instructions. Its state
(frame, base, the VM itself) was kept in memory and loaded again in some 1,100 places; which of
them kept a register changed with any edit (moving two stores spilled ip itself: +3% to +18%).

**The instructions as functions** (3a7056f, 8bb9f96, 5140de5, 9567d77, fe21996). run()'s cases
moved to src/instructions.inc, written once with their ways out named (DONE, EXIT_RUN, JUMP_LABEL,
CASES, FALL_INTO, GO_COLD). Built with Clang 19 or later, each is VM::tail<op>, a function that
calls the next instruction's as its last step (preserve_none, musttail), with ip, sp, base,
frame, consts, caches, code and the VM in registers from one to the next; the code holds each
instruction's function, written as the code is made. Built with MSVC, GCC or an older Clang they
are run()'s switch, as before. A proof on the hot instructions alone (branch m6-tail-proof) ran
numeric 23% faster and the rest up to 18% slower, from going between the functions and run().

What it needed: run()'s base frame kept in the Context (the VM's threads take turns with one VM,
and kept in the VM it was another thread's); three instructions' own values ended before they go
on; no stack protector in the functions; and, built for Windows, where a function that calls
anything sets up its stack frame as it starts whichever way it goes, each hot instruction's rare
part a function of its own (COLD), so that the part that runs makes no call. Only seven
registers are left to an instruction's own work, so a large one is split by kind (RGetProp: an
object's field and an item's here, a value's in a box or held in another in its rare part).

Against the code before them (b37f396), same Clang build, best of five: particles -43%, calls
-27%, numeric -20%, bounce_values -19%, colors -18% to -19%, bounce_moved -14%, fields and
layout_classes -13%, points -10% to -12%, jade_layout -11%, the other layouts -7% to -11%,
simulation -8%, bounce_classes -5%, strings -1%; against group 8, numeric -49%, particles -54%,
calls -42%, fields -38%.
All tests pass with Clang and MSVC in all three ways, with every stress setting and the sanitizer,
and on Linux with Clang 21 (functions) and GCC (the switch).

## Arithmetic chosen by type (step 5)

**Typed arithmetic** (8b52102, D178's second half, G17). Where the checker knows both sides of
`+ - * / < <= > >= == !=`, or of `+= -= *= /=`, are ints, or both floats, it notes the expression,
and the compiler emits an instruction of that type (ADD_I, MUL_F, LT_I and so on: 17 of them).
The translator makes register instructions of them (R_ADD_I_SS, R_MUL_F_SK, R_JUMP_LT_I_SS and
so on: 61), which read the two payloads and test nothing of what the slots hold. An int's sum,
difference and product are still checked for overflow, and an overflow goes the general way, so
its error is the same. An int divided by an int keeps its own rules and stays general, and so
does a pair of mixed kinds such as `2.0 * i`: the general instruction turns the int into a float
there, which is what the program means. An int that may be null is typed once the checker knows
it is not.

Against the tail-call build, same Clang build, best of five: numeric -21.8% (121 to 95 ms),
fields -5.4%, bounce_values -4.8%, the rest -3% to +1%.

Not done: slots that keep only a payload (D178's first half). The general slot's kind byte is
written along with the payload, and a typed instruction reads only the payload, so leaving the
byte out would save one store per result; it waits until timings show that store.

Found on the way, and older than this step: a comparison worked out while compiling, of a NaN
made from constants (`0.0 / 0.0 >= 1.0`), gave true for `<=` and `>=`, where worked out as the
program runs it gives false. The checker compared through an order of -1, 0 or 1, on which a
NaN fell as equal; it compares the numbers as they are now.

## Values in variables (step 6)

**Places** (D149, G13, G19). A local variable whose type is a value type keeps its value in a
place of its frame's, not in a box: `val r = Rectangle(...)`, `val s = child.sizes()`, and the
values made as arguments, `Sizes(Size(1, 2), Size(3, 4), Size(5, 6))`, make no object. D149 said
consecutive slots of the frame; they are places beside the stack instead, which comes to the same
for the program and leaves every instruction that reads slots as it was:

- Each line of execution (a thread, a task) has 3,072 places, made when it first needs one and
  never moved. A function with such variables starts with EnterPlaces, which gives its frame a
  run of them above those of the frames under it; it has them until it returns. A frame for
  which none are left keeps boxes, as before (deep recursion).
- Each place is laid out as a box is, with room for 64 bytes of value after it, and a variable
  holds a Ref to its place. To the interpreter a Ref to a place is a Ref to a box being made: no
  instruction tests which it is. (A first version kept the places as one block, a Ref saying
  where in it; the test that took in `refClass`, inlined into the instructions that read through
  a Ref, made reading an item of a list 75% slower, though no instruction run changed.)
- A Ref is only ever on its stack. What keeps a value longer copies it, as for an item of a list
  (VM::own): a field, a list, a map, a captured variable when its frame ends, a value given back
  (copied into the caller's place where it gave one, WithPlace, or into a box), and a variable
  with no place of its own (KeepLocal: `var keep : any = r`).
- A variable's frame alone changes its place, through it (`p.x = 1`, `p.grow()`, no box made:
  G8) or by giving it another value (SetPlace, a copy into it). A Ref read from it holds while its
  statement runs, unless the statement changes the variable inside it (`f(p, p.also { p.grow() })`):
  there the checker has the read take a copy (KeepTop). A lambda that changes a captured variable
  runs in a frame of its own, and gives the variable a box, so a call given the place meanwhile
  sees it as it was.
- A call's result is made where it goes: in the variable's place, or, for an argument, in one of
  the statement's places; a function giving back a value kept in a place of its own copies it
  into the caller's.

Found on the way, older than this step: a value type with a property worked out by a getter
(`val size : Size get() => ...`, as Rect, Size and Point have) was never made where it goes, the
body's getters counted as fields that keep a value. They keep none now; with places, Jade's
layout makes 42,000 boxes in 1,000 layouts where it made 397,000.

Against the build before it, same Clang build, best of five: layout_values -30%,
layout_cached_values -17%, colors_values -6%, bounce_moved -3%, jade_layout level (with a
tenth of the boxes); the rest within 3% either way.

## A generic value type's type arguments (step 7)

**G4, all of it as decided** (the user's choice, 2026-11-05, over judging by the fields alone; in
three parts: 28353cf, df54f9c, and the workers'). A value of a generic value type keeps the type
arguments it was made with, or that the checker worked out, at no cost in bytes:

- a box beside its class (the box's "being made" flag moved into the spare byte of the object's
  header, Obj::valueOpen), and a frame's place likewise;
- a small value by a number of the VM's in its slot's `refOffset`, which a small value did not
  use; the number is kept on the type once given (ObjTypeInfo::valueNumber);
- an item of a list, or a value kept inside an object or another value, takes them from the
  list's or the field's declared type, made for the object's own type arguments;
- a phantom type parameter, which no field shows (`value Id<T>(val raw : int)`), where it is
  kept in a container declared wider than such a parameter can be (`List<Id<any>>`, a field
  `Tag<any>`, a value's field `Id<any>`), in a hidden 8-byte slot beside the item or field
  (option B); elsewhere nothing, the declared type saying it already.

A field's type for any type arguments is made, without running the program, from patterns: each
class whose fields need it has a function giving its fields' types (FieldTypesMaker, from the
checker's types as reflection makes them), run once, as the first object or value of the class is
made, with stand-ins for the arguments (kTypeHole). A first version ran it wherever a type was
asked for; under the GC stress setting that re-entered the interpreter from inside instructions
not ready for it, and a function the collector had not been told the class held was freed.

`is` and `as` go by the kept arguments, refined by what the fields hold where those are wider
than asked; a cast to narrower ones gives a copy keeping those; reflection and a failed cast's
message show them; == and keys do not look at them. A value sent to a worker carries its type,
found again there, and a list keeping its items' types beside them goes item by item. A place
that makes such values finds their type through the type arguments it was given
(ObjTypeInfo::madeAs). No benchmark moved.
