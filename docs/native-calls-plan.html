Plan: calls from native code to native code

Written 2026-11-15, at the user's word ("ok", to: calls made by native code start as a plan, its spike to show a call from native code to native code costing less than the VM's own). A function's region calling another function whose own region is made, from machine code to machine code: the callee's frame pushed by a step, its machine code entered at once, its return a step that comes back. It follows the plan for calls made from native code (2026-11-13), whose spike failed its gate, and native code for whole functions (d09b55e), which is what makes another way possible now. Questions for the user at the end, each with a recommendation; nothing is built before they are decided and the spike passes its gate.

What it is

Today a region cannot make a call. At a call it writes back what it holds in registers and leaves for the VM; the VM makes the call; the callee's own region, if it has one, is entered through VM::nativeEnter (its context made anew) and left at its return for the VM again; the VM returns, and comes back into the caller's region at the instruction after the call, which loads its registers again. Four ways in and out of native code for one call, and the VM's call and return between.

The plan: where the callee's region is made and the call is one the VM would make at once (its quick call), the caller's region pushes the callee's frame itself and runs the callee's machine code; the callee's region, coming to its return, does the VM's quick return and comes back to the caller's machine code, which goes on. The VM is not in it at all. Anything the quick way does not cover leaves for the VM as now.

A program behaves the same with it as without it: answers, errors and their messages, stack traces, other threads' turns, collections, tasks that wait, how deep recursion goes. Every test runs with native code, with the VM alone and in the interpreter, as now.

Of mix16's 14.7 ns a call: the loop's region leaving at the call (its registers written back), the VM's quick call (the frame pushed, the two parameters checked), nativeEnter finding the callee's region and making its context, the callee's region leaving at CHECK_RETURN, the VM's check and return, and the VM coming back into the loop's region (nativeEnter again, its registers loaded). How it splits between them is to be measured by the spike, not guessed here.

Why the spike of 2026-11-13 failed, and what is different now

That spike made the call from the caller's region by a C++ helper that pushed the callee's frame and ran the VM's loop until it returned. The VM's own quick call was 13 ns, call, callee and return; the region's side alone was 8 ns (its registers written back and loaded again), the helper 3, and the run of the loop 14: about 20 ns against 13. The gate was a call made from native code costing no more than the VM's quick call; it failed, and leaving and coming back was made cheaper instead.

What is different now: callees have regions of their own (d09b55e). The callee need not run in the VM at all, so there is no loop to run anew and no nativeEnter, and the caller need not write back what nothing but itself reads: a value in a register that the callee cannot see stays in the caller's register (saved on the machine stack by the call step, as any C++ function saves what it keeps across a call). What is left to pay is the frame pushed, the arguments in their slots, the jump into the callee's code and back, and the callee's context.

A call from native code to native code

The call step

  • What it checks, as the VM's quick call does: the callee is the function the region was made for (the global, or the method the object's class has, read and compared with what it was); its region is made; the arguments are all given (no default left to fill in); there is room for a frame and on the stack; no collection is due and no other thread waits (the flag); the call wants no place for its result. Anything else: the region leaves at the call, as now.
  • What it writes: the arguments into their slots (where the callee's region reads its parameters); the caller's frame's ip to the instruction after the call (for stack traces and handlers, as the VM sets it); the callee's frame (frames_[frameCount_]: its closure, ip, base), and the frame count. The VM's frames and stack are read and written through the context (RegionContext gains the VM's frame array, count and limit, the stack's end, the collection's numbers).
  • The callee's machine code entered at its region's head, past its parameters' prologue (the checks of each parameter's type the call step makes instead, as the region knows the arguments' kinds), as a function the step calls, its own registers: what the caller keeps in registers across it, the step saves and loads again (Clang does this in the stencil, as for any call).
  • The callee's context: its own (question 3). A region reads per frame its closure's captured variables (upvalues) and its places (places); the rest (the flag, the core, the globals, the allocator, the keys' count) is the caller's.

The return step

A whole function's region today leaves at its return for the VM. Entered by a call step, its return does what the VM's quick RETURN does where it may: no variable of the frame captured (no open upvalue at or above its base), no handler of its own left, its result wanted and no Ref: the result into the frame's slot 0 (where the caller's call put the callee), the frame count back, and back to the call step with the result. The call step puts it where the call's result goes and the caller's region goes on. Entered by the VM (nativeEnter), the same region leaves at its return as now: how it was entered is passed in the context.

When the callee cannot go on in native code

The callee's region may leave for the VM: at an island (an instruction it leaves to the VM), at a miss (a guess wrong), at a loop's flag, at a return the quick way does not cover. Its frame is pushed and the VM's state is right for it (its slots written back, as at any way out). Two ways on (question 4):

  • The caller leaves too (recommended): the call step writes back the caller's registers (which it holds, saved, after the callee's code returns to it), and returns to nativeEnter the callee's instruction and top, marked as another frame's. The VM goes on with the callee, makes its return as it always does, and comes back into the caller at the instruction after the call, which is a way in of the caller's region (as after an island today). No run of the VM's loop inside native code, no C++ frame between: an exception, a collection, another thread's turn and a task that waits all happen in the VM as they do now. Native code never has anything thrown through it, so it needs no unwind information.
  • A run of the VM's loop for the callee (the spike of 2026-11-13's way 1), coming back into the caller's code: native code on the C++ stack under the VM, which needs exceptions kept and thrown at the call or unwind information, and a task that waits cannot be set aside.

The same way where the callee's code itself makes a call that leaves: each level writes back and leaves in turn, innermost first, and the VM goes on with the innermost frame; each caller is come back into at the instruction after its call.

Depth. Each call from native code to native code is a C++ call: the machine stack grows by the callee code's frame (a few hundred bytes) for each level. The VM's frame limit (20,000) is checked as the quick call checks it, and below it a limit of native levels (question 5): past it the call leaves for the VM, which makes it as now, so recursion goes as deep as it does today and the machine stack never runs out first (the main thread's is 16 MB; other threads' and tasks' may be smaller).

Which calls

  • A function by name (R_CALL, CALL of a global closure; INVOKE_IMPLICIT where the name is no member, as made values are done since f8bb654): the global read and compared with the closure the region was made for.
  • A method (R_INVOKE, INVOKE, INVOKE_OWN): found by name in the class of the object as the region is made; the step compares the object's class with it, and the method the class has (a subclass's override is another class).
  • Not at first: lambdas a function is given (the closure differs from call to call: question 6), calls leaving out defaulted arguments (the callee's prologue fills them in, which the VM does: inkBox() is one; question 7), calls with named arguments or a spread, of a class (a value made, f8bb654's), of C++ functions (the VM calls most at once), of a function whose region looks at lists or fields once (it would have to look again after each call: question 8), of a generic function given its type arguments, of a function that may wait.

Order, and how each step is checked

  1. The spike: calls by name of a function with no defaults left out, whose region looks at nothing once, the callee's code entered as a function; its return the quick one only; anything else leaving the caller's region at the call before it is made (the slow way of question 4 not yet built). Timed on the table above. The gate: mix16 called a million times in 13 ms or less (from 21.2: the call at most half of what it costs today), fib(25) no slower than 2.56 ms (with its region made, now that its calls would be its own work), and no row of timings.html, the kernels or the ops benches slower. If it fails, stop and report, as the last spike did.
  2. The slow way: a callee that leaves, the caller leaving after it (or as question 4 decides).
  3. Methods, with the class compared.
  4. The context per frame as question 3 decides; regions that look at lists or fields once as question 8 decides.
  5. Region::worthIt: a call made from native code counted as the region's work, not the VM's, where its callee's region is made.

Each step: a test of its own (answers, errors and their lines, stack traces through native calls, a handler in a caller catching what its native callee's VM part threw, recursion past the native limit, a callee that waits, threads, a collection during a callee's VM part), every answer the VM's alone and the interpreter's; the suite and GC stress; the kernels and the benchmarks against the build before. At the end, ASan (the clang-cl build) and the Linux build, as at a milestone.

What does not change

  • What a program does: its answers, errors and their messages, stack traces (the frames are the VM's own, each with its ip).
  • When other threads take their turns, when the collector runs, that a task that waits is set aside, how deep recursion goes.
  • The run code, the VM's calls and returns, ww --interpret, WW_NATIVE=0 and WW_NATIVE_FUNCTIONS=0.

Risks

  • The callee's context is the cost. A region's context is some 2.9 KB, most of it what loops use (templates' words, lists, held fields, homes for spilled values). Made anew for every call it costs more than the call saves; shared, the callee's spilled values must not land where the caller keeps its own. Question 3 is about this, and the spike measures it.
  • Saving the caller's registers. A region keeps up to nine ints and sixteen floats in registers, all of which a callee's code may use. The call step saves those live across the call and loads them after; with many live it may cost what writing them back did. The spike measures it on mix16's loop (two live) and on one with many.
  • Two ways out of one region. A callee's region left at its return comes back to a call step or to nativeEnter; a mistake there returns a result to the wrong place. Each way is tested, entered both ways.
  • Frames the VM did not push. Everything that walks the frames (stack traces, the collector's roots, handlers, RETURN's checks of open upvalues) must find the frames the call steps push exactly as the VM's own. GC stress and the thread stress setting run each step.
  • Gains narrower than the table suggests. Many calls in the library are of methods with defaults, lambdas, or C++ functions: the first steps reach calls by name and plain methods only.

Questions for the user

Each with the recommendation and why.

1Whether to build the spike

  • Build it, with the gate above: mix16 called a million times in 13 ms or less, fib(25) no slower, no timings row slower.
  • Not now: native code goes as far as it has (calls leave for the VM and come back).

Recommended: build it. What failed last time was the VM run inside the call; the callee's own region takes that away, and the spike shows in a day or two whether what is left (the frame, the context, the registers saved) is cheap enough.

Your decision

2What the caller writes back before a call

  • Only the arguments (and the caller's ip): the rest of what the caller keeps in registers saved by the call step on the machine stack, written back only where the callee leaves for the VM.
  • Everything a way out writes back, as at an island, and loaded again after: simpler, and what made the last spike's region side 8 ns.

Recommended: only the arguments. Nothing but the caller reads its registers while the callee runs in native code (a collection, a stack trace or a handler happens only once the callee has left for the VM, and then the caller writes back first).

Your decision

3The callee's context

  • Split: the context made two parts, what every frame shares (the flag, the core, the globals, the allocator, the keys' count: a few words, the caller's) and what each region uses for itself (its upvalues and places, its homes for spilled values, and for loops its lists, held fields and templates' words); a call step makes the callee's own part on the machine stack, only as large as that callee's region uses (most functions' regions: two words).
  • Shared whole: the callee runs on the caller's context, its upvalues and places swapped in and back: no making, but the callee's spills land in the caller's homes, so only callees that spill nothing.
  • A new whole one per call, as nativeEnter makes: some 2.9 KB of stack, the simplest, likely too slow.

Recommended: split. Each region says what of the context it uses (it says already whether it looks at lists or fields once, since d09b55e); a function's region uses little of it, and nativeEnter gains by it too.

Your decision

4When the callee leaves for the VM

  • The caller leaves too, its registers written back, and the VM goes on with the callee and comes back into the caller after the call, as after an island.
  • A run of the VM's loop for the callee inside the call step, and back into the caller's code.

Recommended: the caller leaves too. Nothing of the VM runs with native code on the C++ stack under it, so exceptions, collections, threads' turns and tasks that wait are as today, and native code needs no unwind information; the cost (a way out and a way back in) is only where the callee could not go on.

Your decision

5How deep native calls nest

  • A limit of native levels, say 256 on any thread (some 100 KB of machine stack at most), past which the call leaves for the VM.
  • The VM's frame limit alone (20,000): up to some 8 MB of machine stack, more than a task's or a worker thread's stack may have.

Recommended: a limit of 256. Recursion deeper than that is the VM's from there on, as all of it is today, and no thread's stack can run out first.

Your decision

6Lambdas

  • Not at first: a call of a lambda a function is given leaves for the VM as now.
  • Each closure's region found as it is called: the step looks up the region of whatever closure it is given (a search, as nativeEnter makes).

Recommended: not at first; looked at again once calls by name and methods are in and measured.

Your decision

7Calls leaving out defaulted arguments

  • Not at first: the VM makes them (photo.inkBox() is one).
  • The defaults filled in by the call step where each default is a constant or a global read once (Color.clear), as the callee's prologue would.

Recommended: not at first; it is the step after methods, and the one inkBox waits on.

Your decision

8A caller that looks at lists or fields once

  • No native calls from it at first: its calls leave for the VM as now.
  • Looked at again after each call: a few loads a call, nothing to know of the callee.

Recommended: no native calls from it at first. Loops that look at lists once are the kernels' hot loops, which have no calls in them; a function's region rarely looks at anything once.
