What ww has now

  • No way to compile and run source as a program runs. A program is compiled before it starts; workers (Worker("primes.ww")) run scripts compiled into the program then (CompilerSession::loadWorker), not text given later.
  • A built program leaves the compiler out (D161: ww build keeps only the sections a program needs; the compiler and the ww command are a section of their own).
  • Workers: a second VM, on a thread of its own, with its own heap; it shares nothing with the program, and messages are copied between them (frozen data shared, D97). The isolation a safe script wants, already built and tested.
  • The Host: every file the program reads or writes goes through the VM's host (host.h); the network and processes through io.cpp, which asks whether it runs in a sandbox (32 places refuse or redirect so: refuseInSandbox).
  • The Sandbox (M6.6.2) is for tests: a block given files of its own in memory, simulated hosts, a clock that moves when told; meant to make failures happen, not to keep a program from what it should not reach. Code in it can still call Foreign (native libraries), open windows, use reflection.

What is wanted

  • A program (run by ww, or built) loads a script, from a .ww file or from text in memory, compiles it, runs it and calls its functions.
  • The script calls the program's API: what the program chooses to give it (a game's functions that are safe).
  • A safe script reaches nothing else: no files, no network, no processes, no hardware (windows, the screen, sound, input, the clipboard), no native libraries; and cannot hang or exhaust the program (a while (true) {} in a game's script must not stop the game).
  • For snips and games: scripts written by players or downloaded with content.

The design

In WinterWolf

// The API a game gives its scripts: an interface, which the script is checked against.
interface DoorApi {
  fun open(door : int)
  fun isLocked(door : int) : bool
  fun say(text : string)
}

val source = FilePath("mods/door.ww").readText()      // or text made in memory
val script = Script.compile(source, name = "door.ww", api = DoorApi::class)   // a ScriptError, with its lines, if it does not compile
val running = script.start(game.doors, safety = Safety.safe, limits = Limits(time = 20.milliseconds))
running.call("onEnter", [playerId])                    // a function the script defines
running.stop()

// door.ww, the script: the API is `api`, typed as DoorApi.
fun onEnter(player : int) {
  if (!api.isLocked(3)) { api.open(3) } else { api.say("locked") }
}

How it works

  • Compiled as the program runs: Script.compile runs the compiler on the text (parser, checker, bytecode) against the standard library ww already carries compiled, and the API's interface. Errors come back as a list of what is wrong and where, never a crash of the program.
  • Run in a VM of its own (question 1), as a worker is: its own heap, its own thread or the caller's, nothing shared. A call from the program to the script, and from the script to the API, crosses between the two VMs: numbers, strings, lists, maps and values of value types copied; frozen data shared; an object of the program given to a script as a handle (question 3), which the script can only pass back to the API.
  • The API, both ways (question 2, decided): an interface the program writes, which the script is type-checked against as it compiles; the program gives an object that implements it, and the script reaches that object's interface members, nothing else of the program. And an interface for what the script gives the program (its onEnter, onUse): the script compiled as an implementation of it, refused as it loads where a member is missing or of another type, and called by the program as any object of that interface (Script.compile(source, gives = DoorScript::class, api = GameApi::class), then running.script.onUse(player)). A function the script hands the API (a callback, api.onTimer(2.seconds) { ... }) is called back in the script's VM, under its limits. The interfaces, with their comments, are what ww doc makes a modding reference of.
  • Safe or trusted (question 4): a trusted script reaches what any program does (a plug-in a user installs on purpose); a safe one reaches only the API and the safe part of the standard library (below).
  • Limits (question 5): each call into the script given a time (or a count of instructions, for a game that wants the same result on every machine); past it the script is stopped at its next safe point and the call fails with a ScriptStoppedException; its heap given a size it may not grow past; its calls a depth. The program goes on.
  • Built programs (question 6): ww build keeps the compiler where the program uses Script, as it keeps Jade's window where it uses that.
  • Native code runs in a script's VM as in any: a script's loops are as fast as a program's.

Snippy on the same VM

Asked 2026-11-19 (the user: "right now snips also supports snippy (a custom python like scripting language), can we have that run on our vm as well?"). A second front end: Snippy's text read by a parser of its own and made into what the VM runs, so that a Snippy script is a Script like any (Script.compile(source, language = Language.snippy, ...)), with the same API, safety, limits and native code. Two ways (question 9): Snippy made into WinterWolf's source and compiled as that (its errors mapped back to Snippy's lines), or into the compiler's tree, or bytecode, directly. Dynamic typing the VM already has (any); indentation is the parser's; Python's ways where WinterWolf's differ (whole numbers without a limit, empty lists and strings false, how a dictionary is gone through) each a small part of the runtime or a choice to be made, from Snippy's own description and its implementation in Snips.

What Snippy is (read 2026-11-19 in C:\Users\sciss\IdeaProjects\Snips, src/main/kotlin/com/snips/snippy: a tree-walking interpreter in Kotlin, 3,448 lines, with 2,484 lines of tests): Snips' own Python-flavoured language for its script blocks. Python's numeric tower (bool within int, of any size, within float within complex, mixed arithmetic promoted as Python does); lists, tuples, dicts, sets and frozensets, slices, comprehensions (eager: no lazy generators); functions with defaults (evaluated at each call, not once as Python does), keyword arguments and lambdas; classes with Python's special methods (__getitem__, __iter__, __next__, __str__ and the rest), the collections.abc mixins written in Snippy itself; exceptions with try, except, else, finally; imports between a document's script blocks; stepping (a run to its n-th statement, again from the start, as a script is a pure calculation: no clock, no randomness). Already safe and limited by construction (no files, network or reflection; SnippyLimits). At its edge, values become Snips' cell values and its errors Snips' (#VALUE!, #DIV/0!).

What WinterWolf lacks for it: whole numbers of any size and complex numbers (neither is in the standard library); classes whose objects gain attributes as they run (the VM keeps such extra fields already, VM::extraField); Python's special-method rules. So Snippy on the VM is a compiler from Snippy to what the VM runs and a Snippy runtime: its values, its operators and their promotions, its equality, hashing, truthiness, str and repr, its built-in functions and methods, written in WinterWolf (whole numbers of any size a class of the standard library's, useful beyond Snippy). Its tests, ported as Snippy files with what Snips gives for each, are the gate: the same answers as Snips' interpreter.

Questions for the user

Each with the recommendation and why.

1A script's own VM, or the program's?

  • Its own (as a worker has): a script cannot reach or change the program's objects, can be stopped or thrown away whole, and its memory counted apart; a call between the two copies what it passes (some microseconds a call).
  • The program's: calls as fast as any, objects shared; but a safe script then shares the program's heap, its stopping is harder, and every object passed is reachable whole.

Recommended: its own, for safe and trusted scripts alike: one design, and the isolation workers already have. A game calls a script a few times a frame, where microseconds do not matter.

Decided2026-11-19, the user ("go with the recommendations for the rest"): its own VM, for safe and trusted scripts alike, as a worker has.

2The API: an interface, or functions registered by name?

  • An interface the program writes and implements: the script is type-checked against it as it compiles (a wrong name or type an error with its line), and the program's other members cannot be reached.
  • Functions registered by name (api.add("open") { door -> ... }): quick to add one; checked only when called.

Recommended: an interface. Script writers get errors where they write, and what is given is written down in one place.

Decided2026-11-19, the user: "yes, interfaces both ways": the API the program gives is an interface the script is checked against; and what a script gives the program is an interface too (DoorScript: its onEnter, onUse), the script compiled as one, refused as it loads where a member is missing or of another type, and called by the program with its types (script.onUse(player)). Functions a script hands the API (callbacks) are called back in its VM, under its limits. Snippy scripts call the same interfaces, checked as each call runs.

3The program's objects in a script: handles, or copies?

  • Handles: an entity given to a script is an opaque value it can only pass back to the API (api.health(enemy)), the object staying the program's.
  • Copies: the object's fields copied into the script's VM; changing them changes nothing in the game.

Recommended: handles for objects, copies for plain data (numbers, text, lists, maps, values of value types).

Decided2026-11-19, the user ("go with the recommendations for the rest"): handles for the program's objects, copies for plain data (numbers, text, lists, maps, values of value types).

4Trusted scripts too, or safe ones only?

  • Both: trusted for a program's own plug-ins and tools (full access, chosen by the program), safe for anything a player or the internet gives.
  • Safe only.

Recommended: both, safe the default: Safety.trusted must be asked for.

Decided2026-11-19, the user ("go with the recommendations for the rest"): both, safe the default; Safety.trusted must be asked for.

5A script's limit: time, or a count of instructions?

  • Time (milliseconds a call): simple; a slow machine stops a script a fast one lets finish.
  • Instructions (a count a call): the same result on every machine (replays, multiplayer that must agree); counting costs a little on loops.

Recommended: both offered, time the default; a game that needs to agree across machines asks for the count.

Decided2026-11-19, the user ("go with the recommendations for the rest"): both offered, time the default; a count of instructions for a game that must agree across machines.

6The compiler in built programs

  • Kept where the program uses Script, found as it is built; a built program that runs scripts grows by the compiler's size (measured in part 1).
  • Always kept.

Recommended: kept where used: a program that runs no scripts stays as small as now.

Decided2026-11-19, the user: "right now a built exe only carries the libraries it needs, so if no scripting is used, the built exes can leave out whats needed to run scripts": kept where the program uses Script, left out otherwise.

7Threads and workers in safe scripts

  • Refused: a safe script runs on the thread that calls it; nothing of it runs after the call returns but what the API's callbacks start.
  • Allowed, counted: threads and tasks within the script's limits.

Recommended: refused at first (coroutines of its own, sequence { }, still allowed: they run within its calls); allowed later if a use appears.

Decided2026-11-19, the user ("go with the recommendations for the rest"): threads and workers refused in safe scripts at first; their coroutines and sequence { } allowed.

8When: before or after the emitter plan?

  • Before the emitter (emitter-plan.html): scripts usable sooner; the emitter after.
  • After the emitter's x86-64 parts.

Recommended: before. It needs nothing of the emitter (a script's VM uses the native code there is), and it is a feature programs and games need, where the emitter is speed and ARM; the emitter's part 1 (ARM64 with the VM alone) can go first or between, as the user prefers.

Decided2026-11-19, the user ("go with the recommendations for the rest"): before the emitter plan: scripts first, then the emitter, then the speed plan's image parts. The same day the formula engine was put between this plan and the emitter (the formula plan, its question 6).

9Snippy: made into WinterWolf's source, or straight into what the VM runs?

  • Into WinterWolf's source: the quickest and easiest to look into (the made source can be read and stepped through); WinterWolf's checker and compiler do the rest; errors mapped back to Snippy's lines.
  • Into the compiler's tree or bytecode: no round trip through text, and Snippy's ways need not be expressible as WinterWolf's source; more of the compiler to learn and keep in step.

Recommended (Snippy read 2026-11-19): into WinterWolf's source made of calls to the Snippy runtime (a + b made SnippyRt.add(a, b), a method call SnippyRt.call(x, "name", [args])), each value any?: WinterWolf's typing has nothing to check there, the runtime holds all of Python's rules in one place, and the made source can be read and stepped through. Its operations then cost a call each, about what Snips' tree-walking interpreter pays; made into bytecode directly, with what the types allow worked out as it compiles, later, where scripts need the speed.

Decided2026-11-19, the user ("go with the recommendations for the rest"): Snippy made into WinterWolf's source of calls to a Snippy runtime written in WinterWolf; into bytecode directly later, where speed needs it.

10The API's source: where the script's compiler finds the interfaces

  • A contract file: the interfaces, and the data they pass, in a file of their own that imports only the standard library; Script.compile(source, api = DoorApi#, gives = DoorScript#) makes the compiler embed it in the program, built programs too; the script sees its declarations.
  • Any file, followed: the declaring file and all it imports, embedded; no rule, but more carried and more of the program seen.
  • Rebuilt by reflection: nothing embedded; but function types, defaults and unions lost, so callbacks cannot be typed.

Recommended: the contract file. Asked when part 2 began: the interfaces had to be compiled into the script, and reflection could not give them back whole.

Decided2026-11-19, the user: the contract file, as recommended.

11The program's objects in a script: interfaces as handles, or tokens?

  • Interfaces are handles: data copied; an object passed where the contract says an interface reaches the script as an object of that interface whose calls run on the real object; functions so too, as callbacks; the script sees none of the object's other members.
  • Opaque tokens: an object reaches the script as a token with no members, only passed back to the API.

Recommended: interfaces as handles (question 3's handles, given members through the contract).

Decided2026-11-19, the user: interfaces as handles, as recommended.
