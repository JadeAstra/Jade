How they are timed

The picture is a 4000 by 3000 photo, 12 million pixels, read from raw RGBA bytes. Each operation runs three times and the best time is kept, in milliseconds, on the Clang build of ww.exe, an i9-14900KF held at 5 GHz. Per-pixel loops are written as a program would write them, in functions of their own, so that native code makes them regions (the second time a loop starts).

ns a pixel is the time now divided by the pixels the operation goes through: 12 million unless the work column says otherwise.

100% C++ (added 2026-11-13, at the user's word): the same work done by a C++ program of its own, bench/kernels/timings.cpp (timings.bat builds it as ww.exe is built, clang-cl /O2): plain loops over the picture's bytes, one thread, no intrinsics (Clang vectorises what it can), its results made new where WinterWolf's are, on the same photo, the best of three on the performance cores. WinterWolf ÷ C++ is how many times longer WinterWolf takes now. already C++: WinterWolf does the work for each pixel in C++ itself, a call or a few from WinterWolf, so a program all in C++ would take what WinterWolf takes. Where a plain C++ loop doing the same was clearly quicker than WinterWolf's C++, its time is given beside it (plain): copy() and toTensor() copied the pixels once more than they needed, pixels[a..b, c..d] grew its list a row at a time, and a canvas's fillRect went through the shape rasterizer; all four fixed on 2026-11-13, at the user's word ("fix the four easy ones"). Plain loops written as simply for the others (greyscale(), blurred, scaled, transformed, blend) were slower than WinterWolf's C++ (rounding with std::round and working in doubles), and are not given.

Where WinterWolf is quicker than C++ (a copy, or map, each making a new result), it is not its code but memory: the C++ program gives a result of 12 to 48 MB back to the system after each round and gets fresh pages the next, each first touched paying a fault, where WinterWolf's collector keeps the memory and uses it again. A C++ map into a new result each round took 5.1 ms, into one used again 2.5; a copy 8.1 against 2.6 (2026-11-13).

What was done for the slow ones

On 2026-11-13, at the user's word ("do 1 to 6"), each with the same answers as before, the pixels of every drawing, turning and blurring compared byte for byte with the build before.

  1. The small accessors inline. get, set and getOrNull on Image and Grid, and Grid.map, marked inline; map makes its cells first and sets them by index. On the way: a generic class's inline method gave its own type parameter any in a call in its body (blank<R>, Box<R>), now what its call gives; native code never ran a loop over a List<byte>, now read and set as Bytes are (12 million Colors into one: 197 ms to 15); a byte set into a list of ints left native code; !! and a value that is a colour or null now native.
  2. image[x, y] = c with a colour passed in. Native code makes op []='s own copy of a parameter passed on.
  3. Drawing a picture. At its own size on whole pixels, a row at a time in whole numbers.
  4. Loops in lambdas. Native code reads a captured variable (R_GET_UPVALUE); a bare name in a lambda that runs on no object, inside functions that run on none (nor in a block copied in place), is compiled as the checker found it rather than looked up as it runs.
  5. transformed and blurred. Sampling in one pass with each place worked out as it is wanted; the convolution with a ring of rows, a pixel's four parts together, the answer written in place.
  6. inverted(). Through mapChannels again.

Left

  • blurred is 1.4 times faster with the same pixels. A blur of its own (both passes in floats, not rounded to bytes between them) would be several times faster but give pixels a level off here and there: the user's to decide.
  • scaled up (7 ns a pixel) and smoothed lines (22 ns a pixel of length) could be faster; not looked into.
  • A half see-through picture drawn costs 4 ns a pixel, the blend's division for each part.
  • PNG and WebP encoding: the compressors' own work, not looked into.
  • Against C++ (the 100% C++ columns): a pixel loop written in WinterWolf takes 4 to 47 times what the same loop takes in C++, most of them 16 to 47 times (3 to 7 ms for 12 million pixels there, vectorised by Clang), the yardstick's loops over bytes now as quick as C++'s (both run whole by loop templates), histogram() 4 times; what WinterWolf does in C++ already is C++'s. copy(), toTensor(), a region of a grid and fillRect were 1.5 to 25 times a plain C++ loop, and are now as quick or quicker (fillRect 2.2 times, its calls from WinterWolf). A see-through fillRect blends at 3.6 ns a pixel, three divisions each; not looked into.
