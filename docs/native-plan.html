What it is

Jade code turned into machine code as it runs, by Jade itself, with no C++ compiler on the machine that runs it: jade something.jade, the shell, workers, tests and programs made with jade build alike. Two levels, built in this order:

  1. Copy and patch. Each instruction the VM runs becomes a piece of machine code made ahead, when jade.exe is built, by Clang from the VM's own instructions.inc (a stencil), with gaps where its operands go. A function's machine code is its instructions' stencils copied one after another, the gaps filled in: the slots it reads and writes, its constants, where it jumps. What the interpreter spends on each instruction besides its work (finding the next one's code, an indirect jump the processor often guesses wrong, reading the operands out of the code) is gone. Values stay where the VM keeps them, in the frame's slots, so the collector, tasks and the VM see everything as they do now; anything a stencil does not handle at once goes back to the VM at that instruction. Expected: loops 3 to 5 times as fast.
  2. Values in registers. Where the checker knows a value is an int, a float or a bool (the typed instructions of M6.7 step 5), and nothing else can see it, it is kept in a processor register across the instructions of a function, not written to its slot and read back each time: loop counters, indexes, running totals. The hot typed instructions get stencils that take and give values in registers; every way out to the VM writes them back first. Expected: loops 1 to 1.5 ns an item, within 1.5 to 3 times of hand-written C++.

The standard library and Topaz are Jade code, and gain as a program does. A program behaves the same with machine code as without it, error messages, stack traces and checks included; the tests show it by running every test both ways.

How Jade runs code today

What this stands on, as M6.7 and M9/M10 left it:

  • Stack code, from the compiler, kept in the program cache, and run code made from it by registers.cpp when a function is first called (the TRANSLATE instruction): stack instructions, and register instructions (R_ADD_I_SS, R_GET_INDEX_SS, R_CALL, ...) that name the frame's slots directly, each with a slow way, the stack code it stands for, written after the function.
  • Frames of 16-byte slots (Value: a kind and an 8-byte payload), which the collector reads, and which a task set aside keeps.
  • Instructions as functions in the Clang build (D160): each instruction of instructions.inc is a function (VM::tail<op>, preserve_none) that calls the next one's as its last step (musttail), the VM's state passed in registers: ip, sp, base, frame, consts, caches, code. The MSVC build has the same instructions as the cases of one switch.
  • Checks the checker could not remove: an int's overflow, an index in range, a byte's range, a narrowed type, each with the message the program gets.

Copy and patch fits this closely: a stencil is one of those instruction functions, compiled with its operands as gaps and its last step a jump to the next stencil.

Stencils, made from the VM's own instructions

  • Operands by name. instructions.inc reads an instruction's operands from the code, ip[0], FAST_U16(4), operandI32(ip + 6). They become named reads, OPERAND_U8(0) and the like, which the interpreter defines as it reads them now and the stencil build defines as gaps: in Clang's machine code a gap is a reference to an outside symbol (jade_hole_a), filled in when the stencil is copied. The interpreter's machine code does not change; the benchmarks show it.
  • The next instruction: NEXT() in a stencil is a jump to a gap, filled with where the next stencil was copied, or nothing where it was copied right after (the jump left out). A jump's target, and the place of each slow way, are gaps the same way.
  • Made when jade.exe is built: one source file includes instructions.inc with the stencil macros, Clang compiles it, and a tool of our own (tools/stencils, in C++, no third-party code) reads the object file Clang wrote (COFF on Windows, ELF on Linux), finds each function's bytes and where each gap is and of what kind, and writes them out as a table compiled into jade.exe. Nothing is compiled when a program runs.
  • Rare instructions need no stencil: their stencil is a way out to the VM at that instruction, which runs it and comes back to the machine code after it.

Running the machine code

  • When a function is given machine code: when its run code is made, at its first call, as now (question 2). Copying stencils costs about what translating does, so the first-run budget should hold; it is measured.
  • Where it goes: memory taken from the system for code, written while it is not runnable and made runnable, and no longer writable, before it runs (W^X); shared by the cores of a parallel section, read only.
  • Ways out: every slow way, every way a check fails, every instruction without a stencil leaves the machine code for the VM at that instruction, with the frame as it is, frame->ip pointing at the run code's instruction. The VM's own code then does what it does now (an error with its message, a call, the collector), and the function goes on in machine code after it where it can.
  • Calls: a function with machine code calls another's machine code at once, as QUICK_CALL enters a function now, and the VM's for one without; returns the same way.
  • Errors and stack traces: the instruction a frame is at is written before anything that can fail, as SAVE_IP does, so messages and traces name the same lines. Exceptions are thrown by the VM's code after the machine code has left, never through it, so no unwind tables are needed at first.
  • The collector, tasks, workers, parallel sections: values stay in the frame's slots (until step 6, where registers are written back at every way out), so each sees what it sees now. A safe point is a way out.
  • A switch to run without machine code (question 3), and a dump of a function's stencils, as JADE_DUMP_RUN dumps its run code.

Values in registers

  • Which values: a slot the checker knows to hold an int, a float or a bool everywhere in the function (what the typed instructions already rely on), not captured by a lambda, not read by name by anything the function calls. Numbers are not the collector's concern, so keeping them out of their slots for a while is safe where every way out writes them back.
  • Which registers: those preserve_none passes arguments in, beyond the VM's own state: on x64 some six for ints and six for floats. A pass over each function's run code chooses which slots live in them for which stretch (a loop first), by how often each is used.
  • Stencils for it: the hot typed instructions (int and float arithmetic, comparisons and their jumps, list, byte and field reads and writes, the loop's step; about 40) get variants taking an operand from a register or its slot and giving the result to a register or its slot, made by the same build; every other instruction keeps one stencil, its register values written back before it. The variants are kept to those instructions: that keeps their number in hand.
  • Ways out write every register value back to its slot first, and a way back in reads them again; a call writes back what the callee might see (nothing, for a slot no one else names).

Loop templates

Added at the user's word (2026-11-10): the common shapes of loops, and of the data they work on, made as machine code for the whole loop, not an instruction at a time. Once values are in registers, what a tight loop still spends is mostly what it asks again for each item: which kind of list this is, whether this core may touch it, whether the index is in range. A loop template asks once, at the loop's start, and runs the items with nothing but their work.

The shapes

  • Counted: for (i in a ..< b), with a step or down; the counter, its end and its step in registers.
  • Over items: for (x in items) over a list, Bytes, a grid's cells or a range.
  • Rows and columns: for (y in ...) { for (x in ...) { ... y * w + x ... } } and the index carried along a row (var at = y * w * 4, at += 4): a picture's or a grid's pixels, row by row.
  • A queue or a search: while (head < queue.size), a loop left by return or break at the first item that fits.

What is done once, at the loop's start

  • Each list, Bytes or grid the body reads or writes by index: its storage kind, that this core may touch it, that no parallel band stands in the way; where its items are held in a register. Its size too, where nothing in the body can change it (no call that could reach it, no add or remove on it; another core cannot, by the ownership rules).
  • Index checks: where an index is the counter plus a constant, or the row's index, and the loop's range keeps it inside the list's size, the per-item check is left out. Where that cannot be shown, it stays.
  • A body that turns out to do something else (a check that fails, an overflow, a slow way) leaves the loop for the VM at that item, which does that item as it does now: the same error, the same message, at the same item.

Whole loops made ahead

The commonest bodies are made, like the stencils, by Clang when jade.exe is built, as complete loops for each kind of item, the processor's vector instructions included; the translator recognises them in the run code and uses them in place of the stencils:

  • copy (dst[i] = src[i]) and fill (dst[i] = v);
  • arithmetic with a constant or another list (dst[i] = src[i] * k + c, two lists added), checked for an int's overflow;
  • a value held to a range and made a byte (Math.min(255, Math.max(0, v)).toByte());
  • a lookup through a table (dst[i] = table[src[i]]);
  • a total, the least or greatest, a count of those that fit (sum += f[i], if (x > best), if (p) n += 1);
  • the first that fits (if (items[i] == v) return i).

An overflow found in a vector loop is found in the item it happened in, and that item left to the VM, so the message is the one the item gives now. The same templates are what a tensor expression worked out in one pass, without a tensor for each step, can be built on, when pictures and tensors are looked at again.

Expected: a loop with its checks done once, 0.5 to 0.8 ns an item; a loop made ahead, the speed of the same loop in C++, vector instructions and all (a byte copy some 0.05 ns a byte, against 7.3 in the VM now).

Kept with the compiled program

A program's machine code is kept in the program cache beside its compiled program, on this machine only, as D145 already allows (it never goes with the script): a second run copies it in and fills in the addresses that differ from run to run (the VM's own functions, the stencils' helpers), and starts at native speed. Made again when jade.exe changes, as the compiled program is. Workers' programs and a program made with jade build keep theirs the same way.

Systems, processors and the two builds

  • x64 Windows first (this machine), then x64 Linux, both built with Clang: the same stencil source and the same tool, reading ELF; the calling conventions differ, which preserve_none mostly hides (question 4).
  • ARM64 later: the stencil source does not change; the tool learns the other machine's gaps.
  • The MSVC and GCC builds are suspended (the user, 2026-11-10): Jade is built and checked with Clang alone, on Windows and on Linux, so machine code needs no answer for either. Their code (the interpreter's switch, and computed goto for GCC) stays, for when they come back.

Order

Each step committed with its tests; only the Clang Windows build checked step by step, the full check (ASan, now through Clang, the stress settings, Linux) at the end.

  1. The spike. The machine code copy and patch would make for the numeric benchmark's loop and for two picture kernels (the gradient and the byte loop above), put together by hand from the handlers' machine code, with every check and way out kept, run beside the VM and C++ and timed; and the same with the loop's values in registers, and as a loop template (its checks done once, and the byte loop as a loop made ahead). Nothing in Jade changes. It says whether the targets hold before anything is built (question 8).
  2. Operands by name in instructions.inc, a change of spelling only: the interpreter's machine code the same, the benchmarks within noise of the commit before.
  3. The stencil build and the tool: stencils for the hot register instructions (about 40), the rest ways out; the table in jade.exe; a test that every stencil's gaps are what the tool says.
  4. Running: code memory, copying and filling in, jumps, ways out to the VM and back, calls both ways, errors and traces, safe points, tasks; the switch and the dump; the suite run with machine code for the functions it covers. Benchmarks.
  5. Every instruction a stencil or a way out, the stack code's own instructions included; the full suite both ways, and with the GC and thread stress settings; benchmarks and the start-up budgets.
  6. The cache: machine code kept and filled in again on load; the second-run budget kept.
  7. Values in registers: the choice of slots, the variant stencils, writing back at ways out; the suite both ways; benchmarks.
  8. Loop templates: the shapes recognised; checks done once at a loop's start, index checks left out where the range shows them needless; then the whole loops made ahead, one shape at a time, each with tests of its answers, its errors and the item they come at beside the VM, and timed beside C++.
  9. x64 Linux: the tool reading ELF, the suite both ways on WSL with the Clang build.
  10. The timing table written up beside M10-speed.html: the kernels as Jade loops with machine code beside C++, and what that means for the pieces decided as C++ for speed. Then, at the user's word, the speed of pictures and tensors looked at again.

What does not change

  • The language, its checks and its messages; the stack code and the cache's format for it; the VM, which still runs everything machine code leaves to it, and all of it with --interpret.
  • How a program is run: jade something.jade, the shell, jade test, jade build. Nothing new to install; no C++ compiler on the machine that runs Jade.
  • Anyone with jade.exe alone can still run and build everything (the user, 2026-11-10): the stencils are made once, when jade.exe itself is built, and are part of it; running a program, and jade build making one, only copy them and fill in their gaps. A program made with jade build carries the same stencils and makes its machine code on the machine it runs on (kept in that machine's cache), so it too needs nothing installed. Only building jade.exe itself needs Clang, as it does now; only M14, if it is ever built, would need a C++ compiler, and it stays optional.
  • M14 stays in the plan as it is, for built programs that want the last factor (question 6).

Risks

  • The stencil tool reads Clang's object files: well documented formats, but new code, checked by a test of every stencil.
  • What Clang makes of a handler may change with Clang's version: the stencils are made by the same Clang that builds jade.exe, and the tool refuses a gap it does not know, so a change shows at build time, not at run time.
  • Register variants are where the work grows; kept to the hot typed instructions.
  • Two ways of running to keep the same: every test run both ways doubles the suite's time (the runner already runs in parallel).
  • Code placement: the VM is sensitive to where its handlers lie (numeric moved 7% today with one new handler); step 1 is benchmarked on its own for that reason.
  • Start-up: copying stencils at the first call costs; measured against the first-run budget at step 3, and the cache answers it for later runs.

Left for later

  • ARM64.
  • An optimizing level: inlining across functions, checks of indexes the loop proves in range left out, work moved out of loops, the processor's vector instructions. Where M14's C++ compiler would do this for built programs.
  • A loop already running in the VM switched to machine code partway (on-stack replacement): with machine code made at the first call, only a function's first call misses it.
  • Unwind tables, so that an exception may pass through machine code; not needed while the VM throws them.
  • Machine code for the C++'s callbacks into Jade, and for workers' start.

Questions for the user

Each with the recommendation.

  1. The milestone's name and version. It goes between part one and part two of M9/M10. Recommended: called M9.5, with no version of its own: M9/M10 still ends at 0.10.0, which it is part of the way to.
  2. When a function is given machine code. Recommended: at its first call, when its run code is made, as now; if the first-run budget suffers, at its second call instead (a function called once runs in the VM).
  3. On by default, and the switch. Recommended: on for everything (scripts, the shell, workers, tests, built programs); off with jade --interpret or JADE_NATIVE=0; the test runner runs every test both ways.
  4. Linux. Recommended: in this milestone, after Windows (step 7), so that Jade stays the same on both.
  5. The MSVC build. Decided (the user, 2026-11-10): suspended; on Windows the work is done and checked on the Clang build alone.
  6. M14. Recommended: kept in the plan as it is, and looked at again with this milestone's timings.
  7. Registers. Recommended: as many as preserve_none gives beyond the VM's own state (on x64 about six for ints and six for floats), for ints, floats and bools only.
  8. The spike as a gate. Recommended: if copy and patch is less than 2.5 times as fast as the VM on the spike's loops, or registers less than 5 times, stop and report before step 1.
  9. Kept in the cache. Recommended: yes, beside the compiled program, on this machine only, made again when jade.exe changes.
  10. New names. --interpret, JADE_NATIVE, JADE_DUMP_NATIVE, and tools/stencils. Recommended as written; the user's to settle.
  11. Loop templates (above). Recommended: after values in registers (step 7), checks done once for every loop first, then the whole loops made ahead in this order: copy and fill; arithmetic with a constant or a list; held to a range and made a byte; lookup through a table; totals, least and greatest, counts; the first that fits; and the rows-and-columns shape for pictures. The order may change with what the picture code and the kernels show they use most.
