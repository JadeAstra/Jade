Plan: native code made on another core while the VM runs on

Written 2026-11-17, at the user's word ("look at background building first"), after the first call's cost of making regions was cut (0.9.5006, f1c0b48). Regions are still made on the core that runs the program, which stops while they are made: on the first GIF, 14 ms of its 50. Made on another core instead, the program would go on in the VM meanwhile and take the native code once it is ready. Measured below by a simulation; one spike and its gate; nothing built before the questions at the end are answered. All four answered as recommended (2026-11-17). Built the same day: the first GIF 50 ms to 39.5, the same native code (below).

What the first call costs now

  • When regions are made: a loop's the second time round its first run (VM::nativeFirst, at its head), from the frame as it is then; a whole function's at a return after its 64th call (VM::nativeReturn); a region dropped past its misses' limit, once more. Each time on the core that came to it, under one lock, the program waiting.
  • The first GIF (the photo at 1000 by 1000, a fresh process): 50 ms, the calls after it 36. 30 functions' regions made in 14 ms: analysis 3.2, liveness 1.3, registers 4.1 (colouring 2.2, spilling 0.8, liveness again 1.1), the code made 2.4, setting up 1.3; 11 attempts refused. The LZW loop's the most (2.8 ms), then __paletteOf's ten loops (8 ms between them).
  • The VM alone (WW_NATIVE=0) takes 125 ms on every GIF: on this work native code is 3.5 times as fast.

What making regions elsewhere would gain, measured

A simulation (scratch, not kept): regions made as now, but each loop's way in written only when a builder on another core would have had them ready, one builder taking the loops in turn; while it waits, the loop runs in the VM, its head its own instruction (one time round in 256 looking at the clock). The time spent making taken off the call's time. The first GIF, six runs each:

So some 11 of the 14 ms the first call pays over the later ones. It is no more because a loop waiting for its region runs at the VM's speed meanwhile; it is that much because most of the making goes to loops that run little once made (__paletteOf's, and the 11 refused, which then cost nothing), while the loops that run long wait a short time against their run. One builder comes within 2 ms of the bound: more would gain little here.

Beside the time: a program with a window would no longer stop for a region (14 ms is most of a frame at 60 a second).

What the making reads of the running program

To run beside the program, the making may read nothing the program changes as it goes on. What it reads now (src/native/regions.cpp):

  • The frame's slots, and deep into what they hold: a list's class, whether it is packed, its store, its items' class, its first item; an object's fields where a place's cache says; an iterator's source; a value's class (some twenty readers, lines 490 to 900, and five places in the analysis). The program changes all of these as it runs: a list that grows moves its items; a field is set; a collection frees what is no longer held. Made safe by: what the frame shows taken on the running core as the build is asked for (each live slot's kind, and for a list, an iterator, an object or a value what the readers ask of it; a few dozen bytes a slot, microseconds), and the readers reading that instead.
  • The globals (nativeGlobalsSeen, one for the process now, set for the making under its lock), and whether a bare name is a member of this (noMemberForRegion, which asks the VM). Made safe by: the globals copied with the frame's facts, and the answers for the function's bare names worked out on the running core beforehand.
  • Places' caches: read atomically already; one that changes after is a guess the region checks, as now.
  • What the facts point at (classes, their fields' layouts, strings): kept from the collector, as roots, until the build's regions are put in or dropped.
  • The making's own state: its time counters, stepProfiles (for WW_PROFILE_NATIVE) and the executable memory, used by one builder at a time; maybeNullFacts is a thread's own already.
  • Publishing (the function's list of regions replaced whole, then each way in written as one aligned word) is made already for several cores running the function as its regions come: unchanged. (Wrong, found 2026-11-18: a word starts wherever the instruction before it ends, and one across two cache lines could be read half written; the builder now writes none: outstanding.html, o-pstress.)

How it would go

  • Where a region is made now, the running core takes the frame's facts, hands the build to the builder and goes on in the VM, the loop's head its own instruction again (nothing paid while it waits).
  • One builder thread, started with the first build (a program that makes none starts none: start-up as now), taking builds in turn and putting each one's regions in as now. A loop that ends before its regions are ready has them the next time it starts.
  • As the program ends: the builder told to stop and waited for (at most the build under way, a few ms); builds not begun dropped.
  • WW_NATIVE_BACKGROUND=0: made in place, as now. WW_NATIVE_BACKGROUND=wait: made by the builder from the facts while the program waits, for checking (below).
  • Every core of a program (threads, parallel) hands its builds to the same builder.

The spike and its gate

The spike: the frame's facts, the builder and the settings above built. Its checks: every test's native code dumped (WW_DUMP_NATIVE), made in place and made from the facts while waiting: the same, which shows the facts hold all the making reads; the suite on Windows and Linux, in place and in the background; ASan, thread stress, GC stress.

Gate: the first GIF 41 ms or less (from 50); the calls after it, the kernels and bench/run.ps1 no slower; ww.exe's start-up no slower.

Then written into this page, timed, committed (a version a build) and reported; registers plan part B after, on the user's word.

The spike, built: its gate reached (2026-11-17)

Built as planned, in 0.9.5007, with two changes from the plan found on the way:

  • The making reads more than the frame's slots. Beside the twenty readers, the analysis follows what the code reads: an object read from a field or a global is kept as a fact, and its own fields read in turn (image.cells.cells), as deep as the code goes. So what is taken (NativeSeen, bytecode.h; takeSeen, regions.cpp) follows the objects as the function's code may: from the frame's live slots and the globals the function reads (RGetGlobal, GetImplicit, InvokeImplicit), a list's first item (a list of values), an iterator's source, an object's fields whose names the function reads (GetProp, GetOwn, their slow ways too), at most 4,096 objects and 12 deep. A list as its store, kind of item, width and length; an object as its bytes to its slots' end and the slot of each name; a variable's place as its type and class; whether each bare name is a member of this. Every object it names kept from the collector (roots, VM::markWaitingBuilds) until the build is made. The making reads only that, in place too, so the code is the same either way.
  • Two locks. One lock at first, for both the loops' states and the making: a core coming to its next loop waited for the builder's build to hand its own on (the first GIF 46 ms). Now the making has its own lock, and a core takes the short one only (nativeStates): 39.5.

And one fault found by the suite in the background, fixed: a program goes before its VM (run.cpp, command.cpp declare it after), so the builder could still be putting regions into its functions as they were freed (six tests crashed as they ended). A program now drops the builds of its functions as it ends, waiting for one under way (~Program, Builder::dropFunctions); a VM drops those it asked for, which read its objects, and a loop's is asked for again by the next core to start the loop (cores share functions).

Questions for the user

Each with the recommendation and why.

1What the builder reads

  • The frame's facts, taken on the running core (above): the whole making moves to the builder.
  • The live frame, the analysis in place: the analysis (3.2 ms, the part that reads the frame) stays on the running core, the rest goes to the builder. Less to change; some 4 ms of the 11 kept.

Recommended: the facts. The readers are in one place, and the check above (in place against from the facts, the same code) shows if one is missed.

Decided2026-11-17, the user ("go with the recommendations"): as recommended.

2How many builders

  • One.
  • Several (up to a quarter of the cores), each build on the first one free.

Recommended: one. Measured within 2 ms of no cost at all on the GIF; several would add the order between builds to think about, for little.

Decided2026-11-17, the user ("go with the recommendations"): as recommended.

3The suite's runs: in place or in the background

  • In place for the suite's every run (the runner sets WW_NATIVE_BACKGROUND=0), and one more run in the background at each major check, with the stress runs.
  • In the background always, as programs run.

Recommended: in place, with the background run at major checks. Most tests' loops would end before their regions were ready, so in the background the suite would no longer test native code; in place it tests it as now, and the background run tests the builder.

Decided2026-11-17, the user ("go with the recommendations"): as recommended.

4On for every program?

  • On unless WW_NATIVE_BACKGROUND=0.
  • Off unless asked.

Recommended: on. It is what makes a first call quick and keeps a window's frames from stopping; the cost is a second core busy for some milliseconds as a program starts its loops.

Decided2026-11-17, the user ("go with the recommendations"): as recommended.
