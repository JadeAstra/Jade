M6.6 so far: what is left open

The choices made while building M6.6 that are not yet confirmed, and the gaps it left, each with where it is to be dealt with: the first half, parts 1 to 7, and of the second half, part 8's groups as they are built. Written 2026-10-19, and brought up to date after each part since: the gaps they closed are gone from the list. The same items are in gui-plan.md (the M6.6 notes, D162 to D180 and the Open list); the design is in value-lists.html.

Choices to confirm

D162The type of items.itemType (part 1)

Part 1 built a new built-in type, Type, for a type as the program runs. Since 2026-10-24 that is a Class (D48), one thing for one thing: items.itemType, map.keyType, map.valueType, values.itemType, a class's typeArguments, a field's and a parameter's type and a method's result give a Class (any# for a collection made without its type). So items.itemType == int#, and .name and isInstance work on each. Type is the standard library's own; written elsewhere it is an error saying to use a Class.

Decided2026-11-03: Already decided: D162, 2026-10-24 (a Class, not a Type); the text above is brought up to date.

D163How the C++ functions' results are checked (part 1)

By a test setting, not on every call. ASTRA_CHECK_NATIVE_RESULTS=1 compiles a check after every call of an external function against its declaration (the standard library compiled from its source, the cache kept apart); the suite passes with it, and each checkpoint runs it beside the GC and thread stress settings. The C++ is fixed code, so the suite proves its declarations once, and later parts can then trust them while the program runs. The other way, a check on every call, costs every call of the C++. A list or map a C++ function gives is tagged at the call with the type the checker worked out, where it has none.

Decided2026-11-03: Confirmed, with a change: the stress settings (native results, GC, threads, copied reads) go into tests/run.ps1, so that each checkpoint runs them from the repo and not from a scratch script (done 2026-11-04, 4386343).

D164What the check changed in the standard library (part 1)

  • The coerce functions give one of their numbers as it was, so float.coerceIn(Number, Number) and the like say Number, with forms for all ints and all floats that say int and float. (2.5.coerceIn(0, 1) is the int 1.) This is the rule Math.min and Math.max follow too: ints and floats mixed give a Number.
  • A type parameter that the object a call is made on says nothing of (a Map written without type arguments) is unknown, not taken from the arguments: data.get(key, "missing") is no longer typed string? there.
  • Deck.toList (Deque until D183) builds a List<T> rather than casting its List<T?>, and Set == gives false for a set of other things rather than failing at a cast, now that casts are checked in full.
Decided2026-11-03: Confirmed as built (the text above is brought up to date).

D165The rules of a value type, as built (part 2)

  • value Point(val x : int, val y : int) needs a header whose entries are all fields. It is a data class: printing, ==, copy, coming apart.
  • It may implement interfaces, extends no class, and no class extends it.
  • A val field is given its value in the header, where it is declared in the body (one declared there with none is an error), or in the type's init; never again. Since part 4 a var field may be changed, but only through a place that holds the value, or in a mutating fun (D167); elsewhere p.x = 4 is a compile error saying to make a changed copy.
  • === on a value type is a compile error, as a value has no identity; through any it compares contents.
  • A value type cannot hold itself except where that field may be null; the checker reports it.
  • A value is copied wherever it is kept, so no two places share one. Which core may read or change a value in a list is D170's.
Decided2026-11-03: Confirmed as built (the text above is brought up to date with D167).

D179Jade's geometry as value types: decided (part 7)

You chose on 2026-10-19 to make Jade's Point, Dimension, Insets and Rectangle value types, and Jade's Sizes with them: a component's bounds and the sizes it keeps are inside it, and setSize, translate, setLocation, grow and setBounds are mutating methods. Nothing in Jade relied on sharing one; one val that was translated became a var. Since part 8 (group 9) they are the standard library's Point, Size, Insets and Rect; Dimension and Rectangle are errors naming Size and Rect. Sizes is still Jade's.

D180Rect takes all four numbers (part 7)

Rect(x, y, width, height) takes all four, with no defaults. Java's Rectangle() is Rect(0, 0, 0, 0) and Rectangle(w, h) is Rect(0, 0, w, h): both are compile errors as written, so that Rect(30, 40) cannot quietly mean the corner. Rectangle(other) is other, which is copied wherever it is kept. Point(), Size() and Insets() keep their zeros, as in Java. The reason first given, that Astra has no constructors of other forms, no longer holds: secondary constructors came in part 8 (8.9a), and Color has them. Today Rect(30, 40) says only that width and height are missing.

Decided2026-11-03: Confirmed, with a change: still all four numbers, and Rect(30, 40)'s error says that x and y come first, as in Rect(0, 0, 30, 40) (done 2026-11-04, be8950e, 627e517).

D166Lists of values, as built (part 3)

  • A list is packed when it is given its type (by its literal, by what it is declared as, or at the call of a C++ function that made it): List<int>, List<float>, List<bool>, a value type's list, and the nullable ones of those.
  • Putting in a value the list was not made to hold is an error where it is put in (cannot put a value of type string in a List<int>), which an unchecked cast through List<any> used to allow.
  • A copy of a list (toList, slice, subList, reversed, + of two of one type) keeps its type and how it is kept.
  • sortBy and sortByDescending, for every list, call the selector once per item rather than twice per comparison (a million items sorted in 70 to 130 ms instead of 1.5 s). A selector with side effects sees fewer calls.
Decided2026-11-03: Confirmed as built.

D167Changing a value through its place (part 4)

  • A var field of a value is changed only through a place that holds the value: a var variable (local, global, or one a lambda holds), a var field of an object, an item of a list, a value's field that is itself a place, or a lambda's parameter (what forEach { it.move() } is given). So p.x = 4, p.x += 1, pts[i].y++, line.to.x = 9.
  • A mutating fun may change this's fields and call the type's other mutating methods, and is called only on a place. mutating on anything but a value type is an error.
  • A variable or field changed this way gets a value of its own first, so val q = p; p.x = 10 leaves q as it was.
  • Every part of pts[next()].x += 1 is worked out once.
  • Found on 2026-11-03: a lambda's parameter counts as a place wherever it is, but only some functions hand the lambda the item where it is. pts.forEach { it.translate(1, 0) } changes the list; pts.filter { it.translate(1, 0); true }, map.forEach { k, v -> v.translate(1, 0) } and g(pts[0]) compile, and the change is lost. for (p in pts) { p.translate(1, 0) } is an error saying the change would be lost.
Decided2026-11-03: Confirmed, with two changes: a for loop's item over a list is a place too, as forEach's is, so a changing call on it changes the list's item; and a lambda's parameter is a place only where the function hands it the item where it is (forEach, a parallel forEach), elsewhere a changing call on it is the "change would be lost" error (done 2026-11-04, e30f67f).

D168Reading a value where it is (part 4)

  • A value read from a list or another value (pts[i], a loop's item, a lambda's it, a parameter, this) is not copied where the checker shows that nothing which may change a list of its type runs while it is in use, through what the code calls, overrides included. Changing a list means removing, inserting, sorting, setting or replacing items; adding at the end is not, as a reference into a list is by position. A function given as an argument counts as one that may.
  • A loop is judged by its body. If the body gives the item to a variable from outside the loop, the loop is judged by the whole function, as the item might be used after it.
  • Since G10 (2026-10-24), pts[i] used at once (a field read from it, an argument, a comparison) is judged by its statement; kept in a variable, by its innermost for or while loop, or by the function where the statement may give it to a variable from outside the loop; in a lambda, by the lambda.
  • Since G35 (2026-11-02), code copied in from an inline function, and a lambda copied into it, read items where they are as code written there does.
  • A call that may wait counts as one that changes every list, since other code runs meanwhile: a flow that waits in a loop reads each item as it was when the loop came to it.
  • Whatever keeps a value longer than the stack does (a field, a list, a global, a variable a lambda holds, a C++ function) takes a copy.
  • The test setting ASTRA_COPY_READS=1 copies every read; the suite prints the same with it.
Decided2026-11-03: Confirmed as built (the text above is brought up to date with G10 and G35).

D169Results built where they go (part 4)

  • pts[i] = f(...), where f gives a value of the list's type, gives f the item as where its result goes. A function that gives a value passes that on to a call whose result it returns, and making a value from its header alone writes its fields there, every argument worked out before any is written.
  • So pts[i] = pts[i].moved(1), pts[i] = Point(...) and pts[i] = pts[i].copy(x = 4) make no copy.
  • list.replaceAll { it.moved() } replaces each item by what the lambda gives, built where the item is.
Decided2026-11-03: Confirmed as built.

D170Parallel sections over a list of values (part 4)

  • pts.parallelStream() deals each core its own part of the list and hands it the items where they are: forEach { it.move() } changes them there, map and the rest read them there.
  • parallelStream().replaceAll { it.moved() } replaces each item, on every core, built where it is. On a list of anything else it puts what the lambda gave in once every core is done.
  • A core reads and writes only its own part (pts[0] from another core's part is an IllegalStateException saying so), and changes the list itself not at all (sortBy, sortByDescending and replaceAll now count as changing a list, as they should have already). A built-in function given the whole list is refused, but for isEmpty and isNotEmpty.
Decided2026-11-03: Confirmed as built.

ThreadsNo scan at a thread switch (part 4)

The plan was to replace a thread's references into lists by copies whenever it gives up the lock. Not built, and proposed not to be: a thread gives the lock up only at a call or the end of a loop body, and another thread reordering a list meanwhile is a race, which Astra lets give a wrong answer but never damage anything. A reference into a list is checked against the list's length and its type of item every time it is used, so a race at worst reads or changes another item, as it would with objects. A flow is not a race (other code runs at the points where it waits, by design), and the checker handles it (D168).

Decided2026-11-03: Confirmed as built: no scan.

D171Small values in the value itself (part 5)

  • A value type whose layout is at most 8 bytes and holds no object (value Rgba(val argb : int), value Meters(val m : float), value Flags(var on : bool, var shown : bool)) is kept in the value itself: its fields in the 8 bytes a value has for its contents, its type's number beside them.
  • So in variables, arguments, results, fields, lists and maps it takes no box and allocates nothing. The program sees no difference.
  • C++ functions are given one in a box, as they are given every value of a value type; list.add excepted (D174).
  • Measured: bench/colors_values.astra, 100 frames of a 320 by 240 picture blended from a palette, 24 to 31% faster than in part 4, with no box made where part 4 made 15.4 million.
Decided2026-11-03: Confirmed as built.

D172Values inside their objects (part 5)

  • A field of a value type larger than 8 bytes, not null, is kept inside its object, after its other slots, laid out when the first object of the class is made.
  • comp.bounds = r copies the value's bytes in; comp.bounds.w = 30 and comp.bounds.origin.move(1) change it there; comp.bounds = Rect(...) and cached = measure() build it there.
  • A field is laid out so when its type is written, or when it is given a value made by its type's name (var cached = Size(0, 0)). A field of an object made before its class's field types exist keeps a box.
  • A reference into such a field has the same 16-bit offset as one into a list's item, so the 64 KB limit (Size, below) covers it too.
Decided2026-11-03: Confirmed as built. The check of the 64 KB limit (Size) covers these fields too.

D173Fields and results read where they are (part 5)

  • Giving a field of a value type another value counts, for D168, as a change to values of that type, as changing a list of them does.
  • A field kept inside its object is read where it is (a reference into the object) where nothing that may change values of its type runs while the read is in use; otherwise it is copied.
  • What a function gives back that it read where it is stays so where the caller is shown to be as safe; a call's result read at once by one of its fields (node.sizes().pref), and a field given back by return, always are. Elsewhere a function gives back a copy.
  • Measured: bench/layout_cached_values.astra, Jade's layout with each component's Sizes kept inside it, makes 1,215 boxes where part 4 made 57,126; its time is 4 to 7% more, from the reads through references (G14).
Decided2026-11-03: Confirmed as built. The 4 to 7% is G14's, in M6.7.

D174list.add copies where the item is (part 5)

out.add(p) for an item read where it is, in a loop say, copies its bytes straight into out, with no box made for it on the way: filtering a million points by hand takes 43 ms instead of 65. add(i, item) copies the item first, since the items after i move.

Decided2026-11-03: Confirmed as built.

D175Generic functions copied per layout: not now (part 5)

Measured on a million points in part 5: map 46 ms against 41 written out by hand, sumOf 25 against 23, filter 98 against 43, sortedBy 84. The check that generic code makes costs a few percent. filter's difference came from copying each item it hands to its lambda, since the lambda might change the list; inline functions remove that, and copies per layout would not. Inline functions (D59) came in part 8 (group 4), and since G35 (2026-11-02) code copied in reads items where they are: an inline function's body handing each item to its lambda now takes 43 ms against 52 for a plain loop. Copies per layout wait until a measurement asks for them.

Decided2026-11-03: Confirmed as built: no copies per layout until a measurement asks for them (the text above is brought up to date).

D176A number's conversions and Math's functions as instructions (part 6)

x.toInt(), toLong(), toFloat(), toDouble(), roundToInt(), roundToLong(), isNaN(), isInfinite(), isFinite(), and Math.sqrt, floor, ceil, round, abs, and min and max of two ints or two floats, where the checker knows the call is the standard library's, are one instruction each, giving what the library's own gives, errors included. Drawing a million particles a frame is 34 to 40% faster.

Decided2026-11-03: Confirmed as built.

D177Fields kept as their payload alone (part 6)

  • An int, a float or a bool field whose type is known (written, or worked out from what it is first given), and not null, is kept in its object as its 8 bytes of contents alone, before the object's slots, at the same place in every object of its class. An object of three float fields takes 72 bytes in place of 96: a million of them, 112 MB at most against 142.
  • A val, and a field an init must set, has a bit saying whether it has been given a value, so that giving a val a second value, and an init that leaves one unset, are still errors.
  • Any other payload reads as 0, 0.0 or false before it is first given a value, where a slot read as an error. (Only code that reads a field before the line that gives it its value sees the difference; Java's fields do the same.)
  • Field reads and writes are as fast as before, with Clang and with MSVC.
Decided2026-11-03: Confirmed as built.

D149Values in variables, in M6.7 (D178)

Values of up to 32 bytes kept in consecutive slots of a frame (D149) need the same change to how a frame's slots are laid out as frame slots that keep only a payload. You decided on 2026-10-19 (D178) that those, with instructions chosen by type for arithmetic, come with M6.7's rewritten loop. Until then a value larger than 8 bytes in a variable, an argument or a result is a box (gaps G8, G13 and G19).

SizeThe largest value type (from value-lists.html)

Decided "any size, up to 64 KB". Offered on 2026-10-18 and not answered until now: "any size, with a copy on read past 64 KB". The limit comes only from the 16-bit offset in a reference into a list's item or into an object's field (D172), and only fields kept in place count towards it. 8.1aA byte becomes an int by toInt() (part 8, group 1)

D19 says byte arithmetic gives an int and an int becomes a byte by toByte(). As first built, a byte did not go where an int is asked for (b.toInt(), as in Kotlin). Since part 8, group 9 (8.9c) it does: a byte fits where an int or a Number is wanted and becomes an int there. The other way is unchanged: an int literal that fits, or arithmetic on literals, is a byte where a byte goes; a name, even a constant's, is the int it is (val n = 5; val b : byte = n is an error).

Decided2026-11-03: Already decided: replaced by 8.9c, a byte goes where an int does (part 8, group 9).

8.1bWhere a char goes for a string (part 8, group 1)

A char goes where a string is asked for only where Kotlin has a form taking a Char: split(','), indexOf('x'), lastIndexOf, contains, startsWith, endsWith, replace('a', 'b'), padStart(n, '0'), padEnd, each a form of its own taking a char. Elsewhere it is an error saying a string is wanted ("$c" or c.toString() makes one). So a Map<string, V> indexed by a char is a compile error, though when running 'c' and "c" are one key, as a Map<any, V> shows (D25). The other way would be a char taken wherever a string is, made one as it is passed.

Decided2026-11-03: Confirmed as built.

8.1cA char's upper() and lower() give a char (part 8, group 1)

D74 keeps upper and lower over uppercase and lowercase; on a char each gives a char, the letter in the other case where that is one character, the char itself otherwise ('ß'.upper() is 'ß', as Kotlin's uppercaseChar() gives). Kotlin's Char.uppercase() gives a string (for ß, "SS"); ported replaceFirstChar { it.uppercase() } becomes { it.upper() }. Since D74 was built, uppercase() and lowercase(), on a string or a char, are errors naming upper() and lower(); uppercaseChar() gets only "a char has no method".

Decided2026-11-03: Confirmed, with a change: uppercaseChar, lowercaseChar, titlecase and titlecaseChar become errors naming upper() or lower() (done 2026-11-04, be8950e).

8.1dThe UTF-8 a string is made from is not kept (part 8, group 1)

D20: a string's UTF-8 form is made when first asked for and kept. As Python does, a string made from UTF-8 (read from a file, joined by C++ code) keeps only its characters, at 1, 2 or 4 bytes each, and makes its UTF-8 again when C++ code first asks for it: Latin-1 text then takes a byte a character, not UTF-8's two for é. ASCII text is its own UTF-8, so the question is only for other text. Keeping the UTF-8 it came from would save that pass and cost the memory of both forms.

Decided2026-11-03: Confirmed as built.

8.1eThe byte order of Bytes' numbers (part 8, group 1)

L0 gives int16(at), int32(at), float32(at), uint16(at), uint32(at) and their put forms "with a byte order". Built as a flag, bigEndian = false by default (the least significant byte first, as x86 and most file formats keep them; Java's ByteBuffer starts big-endian): buffer.uint32(4, bigEndian = true), buffer.putInt16(0, -2). The other way would be an enum, ByteOrder.big. There is no 64-bit form yet.

Decided2026-11-03: Confirmed; int64 and float64 (and their put forms) are left for M6.7 or after.

8.1fwrap32() beside toInt32Wrapped() (part 8, group 1)

D148 names both, and they give the same: the low 32 bits as a signed number. Both are built; one name for each thing (D74) would keep one, wrap32() for the hashing it is meant for, or toInt32Wrapped() for its family (toByteWrapped, toInt16Wrapped, toUint16Wrapped, toUint32Wrapped), which the errors for a number that does not fit already name.

Decided2026-11-03: One name, toInt32Wrapped(): wrap32() becomes a compile error naming it; rotateLeft32 and rotateRight32 stay (done 2026-11-04, c48ea64).

8.1gWhat hash(a, b, ...) combines (part 8, group 1)

Java's Objects.hash rule, 31 * h + hash of each, wrapping at 32 bits, over Astra's own hash of each value (the one map keys use: by contents for strings, frozen collections, data classes and values), and a class's own hashCode for an object of one (since group 2, 8.2d). The rule is Java's, the numbers are not: hash(1, 2) is -480690409, not Java's 994, as an int's hash is not the int.

Decided2026-11-03: Confirmed; a bug to fix: the rule stays, and with 8.2d's fix an int hashes as Kotlin's Long does, so hash(1, 2) is 994 (done 2026-11-04, 1245c8a).

8.2aThe names FrozenList and open List (part 8, group 2)

D26 and D32 write frozenList, frozenMap, frozenSet and open list. Built after the naming rule, which writes every type but the fixed lowercase set in title case: FrozenList<T>, FrozenMap<K, V>, FrozenSet<T>, open List<T>, open List<accepts Button>. Kotlin's MutableList<T>, MutableMap and MutableSet are errors naming open List<T> and the like, as toMutableList() is one naming toOpenList() (D46).

Decided2026-11-03: Confirmed as built.

8.2bBytes are no key (part 8, group 2)

Bytes can change, so by D26 they cannot be a key, and D26 names no frozen form of them. As built, a key of bytes is refused with the advice key.toList().frozen(), a FrozenList<byte>, which a packed list keeps at a byte an item, as small as the bytes. The other way would be a frozen Bytes, bytes.frozen(), kept as bytes.

Decided2026-11-03: Confirmed as built.

8.2cWhat the checker follows to tell a key that can change (part 8, group 2)

A class with its own == or hashCode can be a key when they read nothing that can change. The checker follows them into the methods and getters they call that have bodies, on the object or on others; a var field read anywhere there makes the class no key, as does a val field of a type that can change, or a call it cannot follow (a function of the C++, an abstract one). A value type may read its var fields, since a value goes into a map as a copy. Getters were followed after Jade's Color, whose == reads its rgb getter, would otherwise have been no key. For Map<any, V> the class carries the answer, marked when compiled (Op::UnstableKey), checked at each new key. Two ways past it were found on 2026-11-03, each class taken as a key: a function that is no member (hashCode() => code(this), with code reading a var) is neither followed nor counted as one it cannot follow; and a subclass's override of a getter the parent's == reads is not followed.

Decided2026-11-03: Confirmed; a bug to fix: follow functions that are no member, and, for each class judged, its own overrides of what == and hashCode call (done 2026-11-04, a194fd3).

8.2dhashCode() for every value, and what hash calls (part 8, group 2)

Every value has hashCode(): a class's own where it has one, otherwise the hash a map takes for it (by contents for strings, numbers, chars, frozen collections, data classes and values; by which object it is for any other), folded to 32 bits. hash(a, b, ...) now calls a class's own hashCode for an object of one, which settles 8.1g's question. An int's hashCode() is the map's hash of it, not the int itself as in Kotlin (5.hashCode() is -57683420). A data class's or a value's hash takes in where its class is in memory, so it differs from one run to the next, where Kotlin's is the same every run.

Decided2026-11-03: Confirmed; a bug to fix: hash the class's name, worked out once per class, so a value's hash is the same every run; and an int hashes as Kotlin's Long does (5.hashCode() is 5), timed on maps of ints (done 2026-11-04, 1245c8a).

8.2eHow deep frozen() goes (part 8, group 2)

frozen() copies a list, map or set, and the lists, maps and sets inside it, all frozen; objects, values and Bytes inside are kept as they are. A frozen collection holding something that can change (a data object with a var, bytes) is frozen, but no key: the checker says so where the type shows it, and the program when it runs. frozen() of a frozen collection gives it back. The type does not go as deep as the copy: [[1, 2], [3, 4]].frozen() is typed FrozenList<open List<int>>, so the checker refuses it as a key though every list in it is frozen.

Decided2026-11-03: Confirmed; a bug to fix: type frozen()'s result as deep as the copy (FrozenList<FrozenList<int>>), so it can be a key (done 2026-11-04, a194fd3, 48c1adf).

8.2fWhich results are open (D45) (part 8, group 2)

Open: what every standard-library function that makes a new list, map or set gives (filter, map, sorted, toList, listOf, mapOf, setOf, split and the rest), a slice, + of two lists, and a vararg parameter inside its function; groupBy gives an open Map<K, open List<T>>. Read-only: emptyList(), emptySet(), emptyMap() (as Kotlin's), what gives its receiver back (orEmpty(), ifEmpty, onEach), a map's keys, entries and values, and what an object hands out of its own (ProcessBuilder.command()).

Decided2026-11-03: Confirmed as built.

8.2gopen is the checker's alone (part 8, group 2)

When the program runs a list is a list: x is open List<int> and x as open List<int> on a value of type any test only List<int>, so a frozen list passes and fails when changed. Frozen collections are known when running: is FrozenList asks the list. Keeping a read-only mark on each list passed through a read-only name is the other way, at a cost on every pass.

Decided2026-11-03: open stays the checker's, but is open and as open refuse a frozen collection as the program runs, at no cost, as the object knows it is frozen; an open list reached through a read-only name still cannot be told, which is right (done 2026-11-04, 130eb53).

8.2hmutableListOf and the like are kept (part 8, group 2)

listOf, setOf and mapOf give open collections already, so Kotlin's mutableListOf, mutableSetOf, mutableMapOf, arrayListOf, hashMapOf, hashSetOf, linkedMapOf, linkedSetOf and MutableList(n) { } make the same thing. They are kept for ported code, though toMutableList() and the MutableList type are errors already (D46, 8.2a); one name for each thing (D74) would make them errors naming listOf. 8.9jHow finely curves are drawn in memory (part 8, group 9)

An image's canvas fills shapes with the text engine's rasterizer, which cuts curves into pieces for small glyphs, to within about a sixth of a pixel at most (a twelfth for the quadratic curves of TrueType fonts): an oval came out 1.6% short of its area. As built, shapes are cut about ten times as finely (three times the pieces), so an oval's pixels add up to its area to within a pixel; glyphs are cut as before, so text draws exactly as it did. Since G64 the rasterizer works out only the rows inside the clip. The graphics card draws ovals by distance in a shader, as before; measured 2026-11-02 (G59), it covers each oval's area to within a pixel too (0.5% on a 6 by 6 one, 0.1% from 20 by 20 up), and the two agree to within 13 of 255 on any pixel of a curved edge, where the card smooths by distance and the image by the area inside each pixel.
