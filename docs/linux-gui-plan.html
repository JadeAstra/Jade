Where it stands

  • The native layer is one interface (platform.h: windows with an OpenGL context, their events, the pointer's shape, the clipboard, waiting, the file dialog) with one implementation, platform_win.cpp (909 lines). Everything above it (drawing, text, the toolkit) is the same code on every system.
  • On Linux ww has no window section: a program that imports Jade cannot open a window, and 30 tests are marked Windows only.
  • Fonts already work there: the text engine reads /usr/share/fonts. OpenGL's functions are fetched by name through what the platform gives (loadGl), so the drawing code needs nothing new.
  • WSL on this machine runs WSLg, a Wayland compositor (WAYLAND_DISPLAY=wayland-0): windows can be opened and tested here. Its compositor is neither KDE's nor GNOME's.
  • The user has a Fedora VM in VirtualBox (KDE Plasma), with D:\Projects\MK_fed shared as /mk.

How: Wayland, and nothing between

KDE Plasma and GNOME both run on Wayland by default, and both speak its common protocols (xdg-shell for windows, and the stable and staging extensions below). One native layer talking Wayland directly, as platform_win.cpp talks Win32, serves both, with no toolkit (GTK, Qt, SDL, GLFW) in between: nothing third-party added, and the window behaving as each desktop's own do. Where the two differ (title bars; which extensions are offered), the layer asks what the compositor offers and does the rest itself.

The system's libraries are opened as the first window is made (dlopen): libwayland-client.so.0, libwayland-egl.so.1, libEGL.so.1, libxkbcommon.so.0, libdbus-1.so.3. ww is not linked against them: on a machine with none (a server, a container) ww and programs without windows run as now, and a program that opens a window is told there is no display, as on Windows with no OpenGL 3.3. The headers are needed only to build (the dev packages; installed in WSL at the user's word).

Title bars

KDE draws a window's title bar and edges itself where the window asks (zxdg_decoration_manager_v1, server-side). GNOME does not offer that protocol: a window there draws its own (client-side). As decided, Jade draws its own on GNOME (and on any compositor without server-side decorations): a bar of Jade's own, drawn by the toolkit with the window's content (a WinterWolf part of the Jade library, as the rest of its controls are), with the title, close, maximise and minimise, the window's menu on a right click (show_window_menu), a drag of the bar moving the window (xdg_toplevel.move) and of the edges resizing it (xdg_toplevel.resize), a double click maximising; and a shadow and rounded corners where the compositor says the window is floating (its tiled and maximised states turn them off). The native layer tells the toolkit whether the compositor decorates (a new PlatformWindow::decorated()); on Windows and KDE it does, and nothing changes there.

What Wayland does not give

  • A window's position. A Wayland client cannot place its window or learn where it is: the compositor decides. position() and setPosition() (and a dialog centred on its owner by the program) have nothing to work with (question 1).
  • A window's icon, in the common protocols: the desktop file names it (and xdg_toplevel_icon_v1 where the compositor has it).
  • Raising a window at will: only with an activation token from recent input, as both desktops guard against windows taking focus.
  • The system's own loop while an edge is dragged (Windows' onIdle): none on Wayland; the program's loop goes on as usual, which is simpler.

How it is tested

  • The suite, on Linux in WSL: the tests that use windows never shown (NativeWindow(..., scale = 1), snapshot(), raw input sent in) run on Linux too, drawing with EGL into pictures: the 30 Windows-only tests made to run on both where they can.
  • Real windows in WSLg, as each step is built: a script opens a window, sends input through the test hooks, and saves what it shows.
  • KDE, in the user's Fedora VM: ww built in WSL and put in the shared folder (/mk) with a script; the user runs it in the VM and its report goes back through the same folder. A build made on Ubuntu 26.04 runs on a Fedora whose C library is as new or newer; where it is not, ww is built in the VM instead (question 3).
  • GNOME: a GNOME session in the same VM, chosen at the login screen (question 2).

Risks

  • OpenGL in the VM: VirtualBox's 3D acceleration is often off or old under Linux guests; Mesa's software renderer (llvmpipe) gives OpenGL 4.5 there, slower but complete. WSLg gives OpenGL through its own driver.
  • GNOME's extensions lag KDE's (no server-side decorations at all; some protocols later than KDE's): each extension asked for and done without where missing.
  • Window position code in programs and in the toolkit (centring a dialog) behaves differently (question 1).
  • D-Bus through libdbus: present on every desktop Linux; where it is missing, no dialog and the default light look.

    • The window stopped answering ("Not Responding", resizes a minute late). Waiting for events answered them too, with the VM's lock let go, so the program's own code ran beside the VM's (found by a watchdog that prints the main thread's stack). Now pump() answers events with the lock held and wait() only waits; the system's resizes are noted and the newest alone is answered; pointer moves are gathered into one; the wait for a frame callback is gone (KWin in the VM never sent them). After it: 225 resizes answered while dragging, maximise and restore at once.

    • The picture against Windows: 315 of 86,400 pixels differ, by up to 6 levels, all in the ovals (the VM's driver); with Mesa's software renderer as under WSLg.
    • VirtualBox's driver. Pictures came out magnified, labels went blank when a button was hovered, a picture drew into a corner of another; Mesa's software renderer drew all of it right. Tests drawn offscreen, compared with the software renderer's pictures, found two causes. First, the driver sends a setting to the device only when it changes, and the device keeps what an earlier program left there: a program run after another drew wrong, the first after the software renderer right. On SVGA3D alone, Renderer::start now makes one throwaway draw with every setting unlike its own, so that its first real draw sends them all. Second, a vertex buffer given new room for each batch was sometimes read from the room it had before: the buffer is now kept from batch to batch (everywhere; no slower on Windows or under WSL, 3,000 batches in 700 and 1,180 ms either way). With both, 14 offscreen pictures right three times running, and the widgets window right by hand. The window's picture also goes onto it as a copy (glBlitFramebuffer, turned over) rather than drawn as a textured square: less work. Three other changes tried on the way (the viewport set twice, the room for a smoothed edge left unread, a clear drawn rather than scissored) did nothing once these two were in, and were taken out.
    • The suite without Jade's tests (suite.sh): 1452 passed, 4 failed, one line of graphics.ww four ways (Segoe UI's bold falls back to the plain face's, so their names are the same): for the fonts, later.
    • To look into a window on Linux: WW_WAYLAND_TRACE=1 (what the compositor sends and how long the program takes; the main thread's stack printed if it is stuck 5 s), WW_WAYLAND_READBACK=<path> (the window's picture saved just before it goes to the screen, once for each size, as raw RGBA), WW_WAYLAND_NO_VIEWPORT=1 (no viewporter or fractional scale).

Step 3: Jade's own title bar, and the system's look followed

2026-11-17, at the user's "ok". Where the compositor draws no title bar (GNOME, and WSLg too), Jade draws one, as GNOME's own windows have it:

  • The native layer (PlatformWindow::clientFrame, setFrame, outerWidth, contentOffset, frameAction, frameState; defaults that do nothing, so Windows needs none): the window's surface holds a bar (46 units) above what can be drawn on and a shadow (24) round it; the compositor is told which of it is the window (set_window_geometry), and the sizes it gives are the window's, the bar in them. A program's size, canvas and pointer stay those of what it draws on. The pointer over the bar comes as Frame events, over the shadow it shows an edge's or a corner's shape and a press resizes (xdg_toplevel.resize); moving, maximising, minimising and the window menu are the compositor's (move, set_maximized, set_minimized, show_window_menu). The window's state (maximised, tiled, full screen, active) is passed on; maximised or tiled, no shadow. EGL's buffer has an alpha now; Renderer::present lays the frame's picture first, then the program's in its place, made solid.
  • The frame (WindowFrame in Native.ww, for any NativeWindow): Adwaita's header bar, light or dark with Palette, paler while the window is not the active one; the title centred and cut short with an ellipsis; the buttons GNOME's button-layout asks for (read through the portal; close alone by default), round, with GNOME's icons (a chevron down, up, a diamond while maximised); a faint shadow, fainter while not active. A drag of a few units moves the window, a double click maximises, the right button gives GNOME's menu.
  • The system's look, followed (the user's choice, 2026-11-17: by default, and as it changes): Palette.dark and Palette.customAccent take the system's light or dark and accent as a program's first window is shown, until the program sets them itself; changes reach a running program (the portal's SettingChanged on Linux, WM_SETTINGCHANGE and WM_DWMCOLORIZATIONCOLORCHANGED on Windows). Windows' own title bar is dark with a dark theme (DWMWA_USE_IMMERSIVE_DARK_MODE). The widgets example follows it too. On Windows the accent is the shade Windows' own apps use (AccentPalette: a lighter one on dark, a darker on light), not the accent itself, which glared on dark (the user, the same day: "the red checkboxes stand out too much"); the test runner's bar is blue while it runs, red or green after, whatever the accent.

Tried by the user in the VM's GNOME session: moving, double click, the window menu, resizing from each edge and corner, the three buttons, maximised and tiled by dragging to the screen's edges, the bar paler when another window is active, the theme followed as it was switched. Matched to GNOME's own look as the user compared them (the shadow made fainter, the icons GNOME's, inactive buttons faded). Windows 1933 passed; WSLg 1593 passed, 3 passed over. KDE, which draws its own title bars, is to be looked at again in its session (the window's buffer now has an alpha, made solid where it is drawn on).
