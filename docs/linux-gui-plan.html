Where it stands

  • The native layer is one interface (platform.h: windows with an OpenGL context, their events, the pointer's shape, the clipboard, waiting, the file dialog) with one implementation, platform_win.cpp (909 lines). Everything above it (drawing, text, the toolkit) is the same code on every system.
  • On Linux ww has no window section: a program that imports Jade cannot open a window, and 30 tests are marked Windows only.
  • Fonts already work there: the text engine reads /usr/share/fonts. OpenGL's functions are fetched by name through what the platform gives (loadGl), so the drawing code needs nothing new.
  • WSL on this machine runs WSLg, a Wayland compositor (WAYLAND_DISPLAY=wayland-0): windows can be opened and tested here. Its compositor is neither KDE's nor GNOME's.
  • The user has a Fedora VM in VirtualBox (KDE Plasma), with D:\Projects\MK_fed shared as /mk.

How: Wayland, and nothing between

KDE Plasma and GNOME both run on Wayland by default, and both speak its common protocols (xdg-shell for windows, and the stable and staging extensions below). One native layer talking Wayland directly, as platform_win.cpp talks Win32, serves both, with no toolkit (GTK, Qt, SDL, GLFW) in between: nothing third-party added, and the window behaving as each desktop's own do. Where the two differ (title bars; which extensions are offered), the layer asks what the compositor offers and does the rest itself.

The system's libraries are opened as the first window is made (dlopen): libwayland-client.so.0, libwayland-egl.so.1, libEGL.so.1, libxkbcommon.so.0, libdbus-1.so.3. ww is not linked against them: on a machine with none (a server, a container) ww and programs without windows run as now, and a program that opens a window is told there is no display, as on Windows with no OpenGL 3.3. The headers are needed only to build (the dev packages; installed in WSL at the user's word).

Title bars

KDE draws a window's title bar and edges itself where the window asks (zxdg_decoration_manager_v1, server-side). GNOME does not offer that protocol: a window there draws its own (client-side). As decided, Jade draws its own on GNOME (and on any compositor without server-side decorations): a bar of Jade's own, drawn by the toolkit with the window's content (a WinterWolf part of the Jade library, as the rest of its controls are), with the title, close, maximise and minimise, the window's menu on a right click (show_window_menu), a drag of the bar moving the window (xdg_toplevel.move) and of the edges resizing it (xdg_toplevel.resize), a double click maximising; and a shadow and rounded corners where the compositor says the window is floating (its tiled and maximised states turn them off). The native layer tells the toolkit whether the compositor decorates (a new PlatformWindow::decorated()); on Windows and KDE it does, and nothing changes there.

What Wayland does not give

  • A window's position. A Wayland client cannot place its window or learn where it is: the compositor decides. position() and setPosition() (and a dialog centred on its owner by the program) have nothing to work with (question 1).
  • A window's icon, in the common protocols: the desktop file names it (and xdg_toplevel_icon_v1 where the compositor has it).
  • Raising a window at will: only with an activation token from recent input, as both desktops guard against windows taking focus.
  • The system's own loop while an edge is dragged (Windows' onIdle): none on Wayland; the program's loop goes on as usual, which is simpler.

How it is tested

  • The suite, on Linux in WSL: the tests that use windows never shown (NativeWindow(..., scale = 1), snapshot(), raw input sent in) run on Linux too, drawing with EGL into pictures: the 30 Windows-only tests made to run on both where they can.
  • Real windows in WSLg, as each step is built: a script opens a window, sends input through the test hooks, and saves what it shows.
  • KDE, in the user's Fedora VM: ww built in WSL and put in the shared folder (/mk) with a script; the user runs it in the VM and its report goes back through the same folder. A build made on Ubuntu 26.04 runs on a Fedora whose C library is as new or newer; where it is not, ww is built in the VM instead (question 3).
  • GNOME: a GNOME session in the same VM, chosen at the login screen (question 2).

Risks

  • OpenGL in the VM: VirtualBox's 3D acceleration is often off or old under Linux guests; Mesa's software renderer (llvmpipe) gives OpenGL 4.5 there, slower but complete. WSLg gives OpenGL through its own driver.
  • GNOME's extensions lag KDE's (no server-side decorations at all; some protocols later than KDE's): each extension asked for and done without where missing.
  • Window position code in programs and in the toolkit (centring a dialog) behaves differently (question 1).
  • D-Bus through libdbus: present on every desktop Linux; where it is missing, no dialog and the default light look.

Questions for the user

Each with the recommendation and why.

1A window's position on Wayland

  • Kept, not used: setPosition remembers what it was given and position() gives it back (0, 0 at first); the compositor places windows (an owner's dialogs centred on it by the compositor, as set_parent asks). Programs run unchanged.
  • Said plainly: position() gives null on Wayland and setPosition does nothing; programs that place windows learn to ask.

Recommended: kept, not used. A program written on Windows runs as it is; what Wayland will not do is the compositor's to decide, as with every other Wayland program.

The spike, so far

2026-11-16. src/jade/platform_linux.cpp: the whole of platform.h but the file dialog and the clipboard (both step 1 and 2), on Wayland: xdg-shell's toplevels, EGL with one OpenGL 3.3 core context (surfaceless for pictures), xkbcommon for keys, text and composing (dead keys), the cursor theme for the pointer's shapes, the whole and fractional scale (with the viewport), server-side title bars where the compositor offers them, the frames paced by frame callbacks on a queue of their own. ww is linked with none of it: ldd ww names only the C and C++ libraries; the protocols' descriptions are made by wayland-scanner as ww is built (CMakeLists.txt).

  • The tests that draw in windows never shown, on Linux in WSL: 26 of the 30 marked Windows only pass there as they are. The other four are about fonts (Segoe UI and Windows' other families, which Linux lacks; DejaVu Sans in their place has other widths): fonts.ww, text_measure.ww, text_draw.ww, and one line of jade_host.ww.
  • A window shown under WSLg (bench/spike/linux_window.ww): visible, at scale 1, its picture the same bytes as the same picture drawn in a window never shown. Against Windows' picture (the same program, text in the same font file): 187 of its 86,400 pixels differ, each by one level of 255, all on the edges of shapes and letters. Windows drew it on the graphics card, WSLg in Mesa's software renderer (llvmpipe): the two round the edges' coverage differently. Byte-for-byte sameness with Windows, as the gate asked it, holds only for one renderer: it is the native layer that is to add nothing, which the shown and hidden pictures show.
  • With no Wayland display: a program without windows runs as before; one that opens a window is told "there is no Wayland display (WAYLAND_DISPLAY is not set): windows need a Wayland session".
  • Built in WSL, ww needs a C library of 2.43 or later (Ubuntu 26.04's): the VM's is checked by the script before anything runs.
  • Left for the gate: the user's Fedora KDE VM (D:\Projects\MK_fed\ww-linux-spike\run.sh, run as bash /mk/ww-linux-spike/run.sh): the picture there, then input, resizing and KDE's title bar tried by hand, into report.txt.
