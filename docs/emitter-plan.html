Where native code stands (0.9.5023)

  • Stencils: src/native/stencils.cpp, compiled by Clang when ww.exe is built, read out of the object file by tools/stencils into a table ww.exe carries (49,739 stencils, about 1 MB of ww.exe's 12.17 MB). As it runs, ww copies the stencils a region's steps name end to end and fills their gaps (native.cpp, the Assembler). Clang is needed to build ww.exe, never to run it.
  • Where it works: Windows, x86-64, Clang builds. MSVC and GCC builds, Linux (the tool reads no ELF) and every ARM computer have none: their loops run in the VM, 5 to 10 times slower (the kernels with WW_NATIVE=0, 2026-11-19).
  • What it is made of: regions.cpp turns a loop or a function into steps (each a stencil's stem and the registers it names), works out what each value is, gives registers (eleven for whole numbers since 0.9.5023, sixteen floats as halves of eight XMM registers), splits a value's life, writes back at each way out only what the VM reads again, and lays out the region's ways in and out. Only its last stage (make) turns steps into machine code; that stage is what this plan replaces.
  • What the stencils cost: preserve_none passes twelve whole numbers in registers, all taken (the frame and eleven values); a stencil that needs one more for its own work keeps the others on the stack about it; a constant is read from a word after the code (movq (%rip)); a comparison makes a 0 or 1 in a register before the jump reads it; each kind of step needs a stencil for each choice of its registers, so the table grows as registers are added (a step of three registers among eleven: 1,331 stencils).

Why an emitter

An emitter writes each step's instructions itself, as ww runs: add r13, r14 written as its bytes, where now the stencil addi_0_1_2 is copied.

The design

What stays

Everything regions.cpp does up to make: the steps, what values are, registers given and split, live slots, ways in and out, counting, templates' recognition. A step keeps its stem and its registers; what changes is what a stem becomes. During the change, a region may have steps of both kinds (question 3).

The encoders

  • x86-64: an assembler for what the steps use: moves, the arithmetic and logic of whole numbers with overflow jumps, shifts, multiplication and division, compares and jumps, loads and stores with base, index, scale and displacement, lea, SSE2 for floats (moves, arithmetic, compares, conversions, sqrt), calls. Labels and jumps fixed up as the region is finished (8-bit where they reach, 32-bit otherwise). About 1,500 to 2,500 lines of C++.
  • AArch64: the same set (part 5); every instruction four bytes, so simpler to encode; constants too large for an instruction built in two to four (movz, movk) or read from a pool after the code.
  • In C++, inside ww.exe: native code is made as the program runs, by the VM. (WinterWolf first holds for what programs run; this is the VM's own machinery, as the stencils' copier is.)

The steps

  • The hot ones written for each encoder (question 2): about 60 kinds (whole number and float arithmetic, comparisons and jumps, slots read and written, lists looked at once and read and set, fields held, moves, loop ends, ways out). Each a function of the step and its registers, writing a few instructions.
  • The large ones as calls: a field read with all its checks, lookAt, a map's or a set's key, the loop templates (runLoop): the C++ stencils.cpp has for them, compiled into ww.exe as ordinary functions (by whichever compiler builds it), called with the registers the step names and the frame. Around such a call, the values alive in registers the platform's calls may change are saved and put back (Windows x64's, the System V ABI's, AAPCS64's). These steps run seldom in a loop's hot path, or do much work each.
  • Registers: x86-64: the frame in a register, one scratch, the stack pointer; the rest given out (13; 14 with RBP, question 4). Floats: all sixteen XMM registers whole, the halves gone. AArch64: the frame, the context and scratch in registers of their own, X18 left alone (the platform's on Windows and macOS), about 24 for whole numbers, 32 for floats.
  • The context stays in the frame, past the function's slots (0.9.5023): every encoder reaches it at an offset from the frame.
  • Going in: a short stub saves the registers the platform's caller expects kept (on Windows x64 seven, more on ARM), only those the region uses, and puts them back on each way out. A whole function's region is entered at each call: its stub kept as short as the registers it uses allow (Vec.dot, a million calls).
  • Code memory: written, then made runnable (Windows VirtualProtect, Linux mprotect); on ARM the instruction cache cleared after writing; on Apple Silicon memory mapped MAP_JIT, writing switched on and off per thread (pthread_jit_write_protect_np).

Each part finished, tested, committed (a version a build) and reported before the next, on the user's word. Then the speed plan's image parts (PNG, WebP; question 1), their new steps written for the emitter only.

How it is checked

  • The encoders' bytes: each instruction form with each register, encoded and compared with bytes kept in the test (made once by an assembler, written into the test: nothing of LLVM needed to build or test ww).
  • Stencil against emitter (parts 2 and 3, while both exist): a setting that makes each region both ways and runs each, comparing the frame and what it gives back, while both exist.
  • The suite: every way and every stress setting, check-live among them (each slot left unwritten poisoned), as now; the ASan build at each part's end.
  • ARM: under QEMU (correct, not timed); timings only on an ARM computer.

What it leaves to other plans

  • macOS: ww has no macOS build and Jade no macOS platform layer; a game on a Mac also wants a Metal renderer behind render.h (OpenGL there is deprecated, stopped at 4.1). Part 5 makes the code ARM's; a Mac port is a plan of its own.
  • Windows on ARM's graphics: OpenGL 3.3 runs there through Microsoft's layer over Direct3D 12; whether that is quick enough for a game is the engine's question.
  • The small fixes to the stencils (constants and offsets built in, a shorter overflow check), proposed 2026-11-19: not done, as the emitter replaces them.

Questions for the user

Each with the recommendation and why.

1Before the image parts, or after?

  • Before (the speed plan's parts 2 and 3, PNG and WebP, after this): what those parts teach native code (hash chains, Huffman tables, bits put out) is written once, for the emitter, and for ARM after; their gates met with 13 registers and flags.
  • After: PNG and WebP sooner, their new stencils written again for the emitter later.

Recommended: before. PNG and WebP keep their C++ encoders meanwhile: nothing is missing, only slower to come; and work done twice is avoided.

Decided2026-11-19, the user ("go with the recommendations"): before the speed plan's image parts (PNG, WebP), their new steps written for the emitter only.

2The steps: written for each encoder, or once over a small machine language?

  • For each encoder: each hot step a function per processor (about 60 kinds, twice); simple, each as good as that processor allows.
  • Once: steps written in a small machine language (load, store, add, compare-and-jump...) that each encoder translates; less per processor, but a layer of its own between, and each processor's best forms harder to reach (x86's memory operands, ARM's three registers).

Recommended: for each encoder, with the large steps shared as C++ calls. Two processors, 60 kinds: the duplicated part is small, and each step can use its processor well.

Decided2026-11-19, the user ("go with the recommendations"): each hot step written for each encoder; the large steps shared as calls to C++.

3Stencils and emitted steps in the same region while it changes, or all at once?

  • Together: steps moved to the emitter a group at a time, each group tested and timed, and each emitted step compared with its stencil; the stencils' conventions kept until none is left (part 4).
  • All at once: the emitter written whole, then switched to.

Recommended: together. Each part stays small enough to find what it broke, and a part that does not reach its gate costs only itself.

Decided2026-11-19, the user ("go with the recommendations"): stencils and emitted steps side by side while the steps are moved, a group at a time (parts 2 and 3).

4On x86-64, 13 registers or 14 (RBP too)?

  • 13: RBP left as the frame pointer: a crash inside native code still shows the stack of calls past it.
  • 14: RBP given out too, saved as the region is entered.

Recommended: 13 first, 14 tried in part 4 and kept only where a loop is measurably faster.

Decided2026-11-19, the user ("go with the recommendations"): 13 registers first, 14 tried in part 4 and kept only where a loop is measurably faster.

5Part 1 (ARM64 with the VM alone) first, or with part 5?

  • First: what does not port is found while it is small, and part 5 starts from a build that passes.
  • With part 5: one ARM stretch of work, later.

Recommended: first. It needs no ARM computer (QEMU), and it tells how much of ww is x86 only before anything depends on it.

Decided2026-11-19, the user ("go with the recommendations"): part 1 (ARM64 with the VM alone, under QEMU) first.
